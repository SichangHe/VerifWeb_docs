## Pitch 1: A Formally Verified Multi-Session Policy Kernel for Single-Process Agent Browsers

* **One-sentence problem + why now:** To avoid Chromium's ~300 MB to 1.3 GB per-worker memory footprint, new headless browsers built for AI agents pack dozens of untrusted sessions into a single OS process, turning any logic bug in URL parsing, cookie handling, redirects, or request filtering into a cross-session compromise (`[Inference]`). Between May and November 2026, the leading agent browser Lightpanda published 11 GitHub security advisories (`GHSA-mq6p-m9cc-q432` through `GHSA-3jpq-xwf3-rwr6`), 9 of which were policy-logic bugs—including miscomputing origins when paths contain `@`, attaching cookies across origins regardless of credentials mode, leaking login headers across cross-origin redirects, violating `SameSite` rules, and leaving CDP/MCP control ports unauthenticated—alongside our newly reproduced bug where `--block-urls` fails to block WebSocket connections (`[Fact]`).
* **Exact thing formally verified and guarantees:** We do not verify the C++ JavaScript engine or HTML layout engine (`[Opinion]`). Instead, we formally verify a ~3,000–5,000 LoC Rust reference monitor ("policy kernel") in Verus that sits between per-session JS isolates (V8 or SpiderMonkey) and the host network/storage layer (`[Opinion]`). Assuming the JS engine enforces memory isolation between isolates and excluding hardware side channels like Spectre (`[Inference]`), the verified kernel guarantees four plain-language properties (`[Opinion]`):
1. *Session Non-Interference:* Session A can never read or overwrite Session B's cookies, DOM storage, HTTP cache, or network responses through kernel state.
2. *Complete Network Mediation:* Every outbound network connection (page load, `fetch`/XHR, redirect hop, WebSocket upgrade, or worker script) passes through the operator's allow/block policy before a socket opens.
3. *Spec-Conformant Origin & Credential Hygiene:* Every URL's origin (`scheme + host + port`) matches the WHATWG URL standard for all inputs; cookies are stored and attached strictly per domain, path, and `SameSite` rules; and `Authorization`/`Cookie` headers are stripped on cross-origin redirect hops.
4. *Authenticated Session Control:* A CDP or MCP controller authenticated for Session A cannot read from or issue commands to Session B.


* **Differentiator vs. prior work:** Quark (Jang et al., USENIX Security 2012) verified a browser kernel in Coq (`[Fact]`), but relied on separate OS processes per tab for isolation and omitted modern WHATWG URL edge cases, `SameSite` cookies, redirect header stripping, and operator blocklists (`[Inference]`). WebSpec (Liao et al., IEEE S&P 2023) modeled browser security invariants in Coq (`[Fact]`), but verified an abstract specification rather than executable systems code (`[Fact]`). Recent 2026 agent-browser security papers—including *Site Isolation is Dead* (Lee et al., IEEE S&P 2026), SPIDES (arXiv 2610.24277), Intact (arXiv 2610.22697), and Prismata (arXiv 2607.08147)—focus on prompt-injection guardrails and information-flow labels rather than verifying the underlying multi-session browser kernel (`[Fact]`). Even Servo's production Rust URL crate (`rust-url`) currently fails 69 of 896 WHATWG standard tests (`[Fact]`).
* **Fit to this group:** Pairs Ghavidel's expertise in Verus/formal control-plane verification (`ZENITH`, 2025) (`[Fact]`) with Madhyastha and Govindan's web measurement and LLM-web infrastructure (`DeGenTWeb`, 2026; NSDI 2026 web archive replay) (`[Fact]`). While a pure PL group can only test a verified kernel on synthetic unit tests, your group can replay thousands of real archived web pages and multi-tenant agent traces through the kernel to prove web compatibility at scale (`[Opinion]`).
* **Bite-sized first paper:**
* *Build:* Write a ~3,000 LoC Rust policy kernel in Verus implementing WHATWG origin parsing, per-session RFC 6265bis cookie jars, redirect header scrubbing, and a unified network mediation gate; link it via C ABI into Lightpanda (replacing its 1,704-line `URL.zig` and request hooks) (`[Opinion]`).
* *Prove:* Machine-check the four guarantees above in Verus with zero `assume` clauses inside the policy path (`[Opinion]`).
* *Evaluate:* Demonstrate that all 9 Lightpanda policy advisories, our WebSocket `--block-urls` bypass, and the 69 `rust-url` WPT failures are statically impossible (`[Fact]` on bug counts; `[Opinion]` on evaluation); benchmark memory and latency across 25 concurrent agent sessions replaying 1,000 real pages from the group's web archive dataset (`[Opinion]`).
* *Duration:* 4–5 months (`[Opinion]`).


* **Biggest risk and what failure teaches:** *Risk:* Reviewers argue that leaving the C++ V8 engine unverified undermines single-process isolation because a V8 memory-corruption bug or Spectre attack bypasses the Rust policy kernel (`[Opinion]`). *What failure teaches:* Auditing the exact FFI boundary (`~10k` lines of Zig glue in Lightpanda; `2,255` lines with `unsafe` in Servo `[Fact]`) defines the exact minimal SFI/MPK hardware cage needed to pair an untrusted JS engine with a verified policy kernel (`[Inference]`).

## Pitch 2: On-the-Fly Binary Verification of Multi-Tenant JIT Sandbox Isolation

* **One-sentence problem + why now:** Browser tabs and serverless edge workers pay a steep performance and memory penalty (~300 MB per tab `[Fact]`) for OS process isolation, yet co-locating untrusted tenants inside a single process requires guaranteeing that dynamically emitted JIT machine code cannot escape its tenant memory cage or tamper with hardware protection keys (`[Inference]`). Today, V8's sandbox assumes an attacker can arbitrarily corrupt memory inside the sandbox (`[Fact]`), Mohabi (Sharma et al., OSDI 2026) incurs a ~25% slowdown on JetStream and Speedometer to isolate the whole engine via SFI (`[Fact]`), Cloudflare notes that arbitrary JIT code can execute `WRPKRU` to disable memory protection keys (`[Fact]`), and our local pilot on `Node v22.21.1` (2,217 instructions across 14 optimized functions) shows that without pointer compression, 32% of JIT memory accesses use raw 64-bit pointers and 32% index off the `r13` isolate root register (`[Fact]`).
* **Exact thing formally verified and guarantees:** Instead of verifying V8's ~2.3M-line C++ compiler (`[Fact]`), we build a formally verified, ~1,500 LoC Verus machine-code checker invoked inside the JIT pipeline immediately before a compiled code page is marked executable (`[Opinion]`). For the concrete instruction bytes emitted at runtime, it guarantees two properties (`[Opinion]`):
1. *Per-Tenant Cage Confinement:* Every memory load and store in emitted machine code resolves to either the current tenant's bounded stack frame, a 32-bit offset added to the tenant's dedicated cage-base register (`r14`), or a verified read-only slot in the tenant's isolate root table (`r13`).
2. *Control-Flow & Protection-Key Integrity:* The emitted instruction stream contains no privileged or protection-key mutation instructions (`WRPKRU`, `SYSCALL`, `INT`) — including inside unaligned multi-byte instruction suffixes — and every indirect jump or call targets the tenant's code cage or an allowlisted runtime trampoline.


* **Differentiator vs. prior work:** VeriWasm (Johnson et al., NDSS 2021) and WaVe (OSDI 2023) statically verify ahead-of-time WebAssembly binaries for a single fixed sandbox (`[Fact]`), whereas JavaScript JITs emit machine code on the fly with deoptimization bailouts, inline caches, and per-isolate root registers (`[Inference]`). Icarus (SOSP 2024) verifies SpiderMonkey's inline-cache stub compiler once offline (`[Fact]`), leaving the main optimizing JIT (`Warp`/`TurboFan`) and multi-tenant isolation unverified (`[Inference]`). Kwon et al. (ISSTA 2024) perform translation validation on V8 IR for semantic correctness rather than binary memory isolation (`[Fact]`). Mohabi (OSDI 2026) walls off the entire JS engine from the browser at a ~25% runtime penalty (`[Fact]`), whereas checking V8 Sandbox pointer-compressed machine code at emission time enforces *inter-tenant* isolation inside one process with near-zero execution overhead (`[Opinion]`).
* **Fit to this group:** Directly unites your core motivation ("paying performance for isolation... every tab is 300 megabytes") with your advisor's exact suggestion ("it would also require on-the-fly verification of the JavaScript code on the page you're loading" and "for the given state, what is the behavior of this?") (`[Fact]`). Uses Ghavidel's verification toolkit (Verus) on a compact binary checker (`[Inference]`) while relying on Madhyastha and Govindan's crawl workloads to evaluate JIT verification latency and multi-tab memory savings on real websites (`[Opinion]`).
* **Bite-sized first paper:**
* *Build:* Compile V8 (`d8`) with pointer compression and V8 Sandbox enabled, resolve the 148 unlabeled call/jump targets observed in our 2,217-instruction pilot (`[Fact]`), and hook a Verus-verified x86-64 linear-scan binary checker into V8's `CodeSpace` allocation path (`[Opinion]`).
* *Prove:* Prove in Verus against a minimal x86-64 instruction semantics that any byte sequence accepted by the checker cannot read or write outside `[r14, r14 + 4GiB)` or execute `WRPKRU` (`[Opinion]`).
* *Evaluate:* Verify that the checker rejects synthetic JIT sandbox escapes (modeled on Wasmtime `CVE-2023-26489`, where a 35-bit address calculation escaped a 33-bit sandbox, and V8 `CVE-2021-21220` `[Fact]`); measure compilation pause overhead and total RSS memory savings across 50 co-located tabs loaded from the group's web archive (`[Opinion]`).
* *Duration:* 5–6 months (`[Opinion]`).


* **Biggest risk and what failure teaches:** *Risk:* Even with V8 pointer compression enabled, TurboFan or Maglev may emit legitimate raw 64-bit pointers for external C++ DOM wrappers or off-heap buffers that a fast binary pass cannot bound without modifying V8's code generator (`[Inference]`). *What failure teaches:* Measuring the exact fraction of instructions that violate strict cage addressing across 1,000 real websites exposes the exact soundness gaps in V8's current sandbox design—a publishable systems characterization on its own (`[Opinion]`).

## Pitch 3: State-Contextual Runtime Verification of Web Archive & Agent Replay Fidelity

* **One-sentence problem + why now:** Web archives, CDNs, and AI agent benchmarks assume that replaying a recorded page or serving a sanitized snapshot preserves live behavior, but subtle mismatches in dynamic state (e.g., prototype pollution, HTML re-parsing, microtask ordering, or URL rewriting) silently break pages and corrupt agent evaluations (`[Inference]`). Madhyastha's group recently demonstrated widespread silent errors when serving archived web pages (NSDI 2026, IMC 2025) (`[Fact]`), while external studies show 15.3% of `FAIL` verdicts in computer-use agent benchmarks (`WARC-Bench` ICLR 2026, `TimeWarp` 2026) are false negatives caused by replay/environment artifacts (`[Fact]`), and our own measurements show 63 of 95 real websites mutate built-in JS prototypes during load (`[Fact]`).
* **Exact thing formally verified and guarantees:** Directly operationalizing your advisor's Nov 3 formulation—*"the runtime verification has the dynamic state context, and that's the difference. The question is, for the given state, what is the behavior of this? As opposed to, for any given state"* (`[Fact]`)—we do not verify arbitrary JavaScript for all possible inputs (`[Opinion]`). Instead, given a *concrete captured page state* $S_0$ (initial DOM tree, cookies, `localStorage`, and archived resource map), we run a formally verified runtime monitor and state-specialized verifier that guarantees (`[Opinion]`):
1. *Sanitized/Archived HTML Round-Trip Stability:* Parsing, rewriting/sanitizing, and re-parsing an archived HTML document under state $S_0$ yields an isomorphic DOM tree containing zero executable script injections (ruling out mutation-XSS bugs like DOMPurify `CVE-2024-47875` and the non-default `ammonia` injection we found `[Fact]`).
2. *Trace-Consistent Event-Loop & Built-In Determinism:* Under concrete state $S_0$, promise microtasks, timers, and spec built-ins execute in strict ECMA-262 order (ruling out the 4,171 of 9,430 test failures and the `"abc".at(-1e300)` integer-overflow crash we found in Boa `[Fact]`), and the replayed page issues the exact same sequence of outbound fetches and DOM mutations as the live recording without leaking requests to live origins.


* **Differentiator vs. prior work:** Static JavaScript verifiers and mechanized semantics (`JSCert`, `KJS`, `ESMeta`) fail to scale to real websites because proving properties *for all states* is intractable when 63 of 95 real sites mutate built-in prototypes (`[Fact]`). Conversely, existing web-archive fidelity tools (Madhyastha et al., NSDI 2026; CCS 2025 *The Power to Never Be Wrong*) rely on empirical heuristics or unverified differential replay (`[Fact]`). By fixing the concrete dynamic state $S_0$ at replay time, universal verification collapses into tractable bounded trace verification (`[Inference]`).
* **Fit to this group:** This pitch has the highest overlap across all three advisors (`[Opinion]`): it directly implements Govindan's dynamic-state runtime verification thesis (`[Fact]`), plugs straight into Madhyastha's NSDI 2026 and IMC 2025 web archive codebase (`[Fact]`), and uses Ghavidel's formal methods toolkit (`[Inference]`). Because it builds on the group's proprietary archive datasets and replay tools, no external group can scoop it on arXiv in three months (`[Opinion]`).
* **Bite-sized first paper:**
* *Build:* Combine our verified HTML sanitizer round-trip checker (`ammonia`/DOM parser model) and our verified event-loop/built-in checks in Boa (or a lightweight V8 trace monitor) into a state-contextual replay verifier integrated with the group's NSDI 2026 archive replay harness (`[Opinion]`).
* *Prove:* Prove in Verus that (a) the HTML archive rewriter/sanitizer is idempotent and script-free on accepted trees, and (b) the replay scheduler preserves ECMA-262 microtask-before-task ordering and origin confinement from concrete state $S_0$ (`[Opinion]`).
* *Evaluate:* Run the verifier across 1,000 archived pages from the NSDI 2026 dataset and `WARC-Bench` tasks, measuring how many silent archive fidelity errors and false-negative agent benchmark failures are caught with mathematical certainty (`[Opinion]`).
* *Duration:* 3–4 months (`[Opinion]`).


* **Biggest risk and what failure teaches:** *Risk:* Real pages may still diverge after initial load due to uncaptured browser APIs (WebGL, Canvas layout sizing, or network timing races) outside the verified state $S_0$ (`[Inference]`). *What failure teaches:* Every unverified divergence pinpoints a missing component in the state snapshot $S_0$, directly improving the fidelity of the group's archive record-and-replay infrastructure (`[Opinion]`).

### Answers to Your Six Open Questions

**"It needs to be something special, something ideally to do with the web, not just PL"**
Pure PL verification targets isolated language semantics, compilers, or data structures (such as `JSCert` or Barrière et al.'s POPL 2023 verified toy JIT `[Fact]`), where hardcore PL groups have a ten-year head start and your systems background goes unused (`[Inference]`). What makes a verification project distinctively *web systems* is proving properties at the messy boundaries where web components meet—such as proving that two HTTP/URL parsers agree on byte framing, that an agent browser kernel mediates every redirect and WebSocket, or that a replayed web archive matches live execution from a concrete state (`[Opinion]`). Your unfair advantage is Madhyastha and Govindan's web crawl datasets, archive pipelines, and measurement infrastructure (`[Fact]`): pairing a compact, machine-checked Verus proof with empirical validation across thousands of real websites (as you already started doing by checking prototype pollution on 95 live sites and linear-time bounds on 28,000 real regexes `[Fact]`) produces an SOSP/OSDI/NSDI systems paper that a pure PL group cannot write (`[Opinion]`).

**"maybe we should do something about security with the agents using the browsers. Although that is also somewhat crowded"**
Your skepticism about crowding is completely validated by the literature (`[Fact]`): between June and October 2026 alone, *Site Isolation is Dead* (Lee et al., IEEE S&P 2026), SPIDES (arXiv 2610.24277), Intact (arXiv 2610.22697), Prismata (arXiv 2607.08147), WASP (221 citations), and BrowseSafe flooded the space of prompt-injection defenses, DOM masking, and dynamic information-flow labels (`[Fact]`). Pitching another label-tracking guardrail invites the exact three-month arXiv scooping your advisor warned about (`[Opinion]`). However, two high-value angles remain wide open (`[Inference]`): first, none of those papers formally verify the *browser policy kernel* underneath the agent (where Lightpanda suffered 9 advisories in cookies, origins, redirects, and CDP/MCP ports `[Fact]`); second, nobody has measured how the live web treats agents at scale with full JS rendering, where our 500-site HTTP pilot already revealed that 38 of 264 reachable sites selectively block agent User-Agents and sites like Reddit and Pinterest return HTTP 403 to OpenAI while serving HTTP 200 to Claude (`[Fact]`).

**"process isolation across browser tabs ... maybe that would be interesting for Cloudflare workers or something like that to share processes"**
Process sharing across tabs and serverless workers is one of your strongest systems hooks (`[Opinion]`), because Chrome's ~300 MB per-tab footprint (`[Fact]`) and Cloudflare Workers' multi-tenant V8 isolate architecture both face the exact same tension between memory density and tenant isolation (`[Inference]`). Crucially, you do *not* need to verify V8's ~2.3M lines of C++ to solve this (`[Opinion]`): V8's own sandbox threat model explicitly assumes an attacker can arbitrarily corrupt memory inside the sandbox (`[Fact]`), meaning isolation requires only that each tenant's heap (`r14` cage base) and isolate roots (`r13`) stay confined and that JIT-emitted machine code cannot execute instructions like `WRPKRU` to disable memory protection keys—a hazard Cloudflare explicitly documents (`[Fact]`). Because Mohabi (OSDI 2026) walls off the entire JS engine at a ~25% performance cost (`[Fact]`) and VeriWasm/WaVe only check single ahead-of-time Wasm binaries (`[Fact]`), an on-the-fly binary verifier for multi-tenant JIT cages inside a single process is genuinely novel (`[Inference]`), provided you explicitly state that hardware side channels like Spectre (which Cloudflare showed can leak 12 bit/s at 99% accuracy `[Fact]`) require orthogonal mitigations (`[Opinion]`).

**"We could argue for agent infrastructure ... efficient browsers ... However, that just are used for light panda"**
Treat Lightpanda as your motivating bug corpus and baseline, not the scope of your thesis (`[Opinion]`). Lightpanda achieves its resource efficiency—about 1.6x faster and 48x less memory one-to-one against Chrome on its single-site benchmark (`[Inference]`)—not through a faster JS engine, but by stripping out pixel rendering and running one V8 isolate per connection inside a single process with pooled memory (`[Fact]`). Every cloud operator hosting thousands of concurrent browser agents will need that exact single-process multi-session architecture to stay solvent (`[Inference]`), yet Lightpanda's 11 security advisories and our unpatched WebSocket `--block-urls` bypass prove that writing the shared session/policy core in unverified Zig breaks web security invariants (`[Fact]`). Because Zig lacks a mature verifier (`zirakzigil` cannot handle general pointers, floats, enums, or recursion `[Fact]`), building a small, Verus-verified Rust policy kernel that embeds cleanly above V8, Servo, or Lightpanda turns a "Lightpanda fix" into the foundational security architecture for multi-tenant agent browsers (`[Opinion]`).

**"I thought we are trying to find things we want to formally verify, right?"**
Yes—formal verification is still the core technical contribution, but in a systems group, *what* you choose to verify must be justified by a systems bottleneck (like multi-tenant memory overhead or archive replay fidelity) where testing fails and a small proof buys a strong end-to-end guarantee (`[Opinion]`). In the November 3 meeting, your advisors were steering you away from intractable, monolithic PL targets—such as verifying an entire C++ JS engine, which at 77k–2.3M LoC is 10–250x larger than `seL4`'s 8,700 lines of C (`[Fact]`)—and toward bite-sized components where verification changes a system's architecture (`[Inference]`). When you verify a 3,000-line multi-session policy kernel (ruling out 9 Lightpanda advisories `[Fact]`), a 1,500-line JIT cage checker, or a state-contextual replay monitor (ruling out Boa's 4,171/9,430 event-loop bugs and `"abc".at(-1e300)` crash `[Fact]`), the systems motivation explains *why* verifying that exact 3,000-line boundary matters (`[Opinion]`).

**"Not sure ... how we turn them into research projects that my advisors would like."**
To get all three advisors excited at once, structure every pitch around a three-part formula drawn directly from their November 3 transcript and recent publications (`[Inference]`): (1) **A small, tractable verification core using existing Rust tools** (satisfying Ghavidel's `ZENITH` methodology and the advice to "pick bite-sized problems... find out what tools there exist" `[Fact]` by using Verus on leaf components rather than building new languages or verifying C++), (2) **Dynamic state or on-the-fly context** (satisfying Govindan's insight that runtime verification asks "for the given state, what is the behavior of this?" `[Fact]`, whether checking emitted JIT bytes before execution or checking replay invariants from a captured page state $S_0$), and (3) **Evaluation on the group's real web data** (satisfying Madhyastha's NSDI 2026 / IMC 2025 work and "we have lots of data, we have lots of experience... you need some differentiator" `[Fact]`). Instead of presenting your 13 or 22 candidates as a flat shopping list of isolated bugs, group them as empirical evidence for one of the three architectural pitches above so your advisors see a 4-month path to a first paper (`[Opinion]`).
