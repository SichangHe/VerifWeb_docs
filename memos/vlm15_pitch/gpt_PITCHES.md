1. “Can we certify the archive rewrites that matter on this page?”

**Problem and why now.** Web archives alter JavaScript to replay old pages, and the group's 2026 FidEx results establish a concrete opportunity to prevent these alterations from changing behavior: the authors report that their fixes “reduced the fraction of archived pages which violate fidelity from 15% to 9%.” [FidEx, NSDI 2026](https://www.usenix.org/conference/nsdi26/presentation/zhu-jingyuan). That is evidence of remaining fidelity failures in their evaluation, not evidence that all remaining failures are formally tractable.

**Exact verification target — proposal.** Build a checker for a restricted family of JavaScript rewrites used in archive replay, starting with URL construction and location reads. Given the original fragment, its rewritten version, and explicit conditions on the current execution state, prove that acceptance implies the two fragments produce equivalent results and side effects under an archive mapping. For example, an original request for a particular URL must become a request for its designated archived counterpart, with the same method and body; exceptions and other modeled effects must also agree. The mapping and allowed observable differences must be written down, not inferred from a passing replay.

Prove the checker sound once; run it on each rewrite; check its conditions immediately before executing that fragment. An example condition is that an operand is a primitive string, so reading it cannot invoke a user-defined getter. If certification fails, ordinary replay may continue, but must be labeled uncertified. We do not yet know how many FidEx failures fit this restricted family. Initially accept only primitive string operations and a small set of modeled browser operations; reject unknown calls, getters, proxies, and other unsupported behavior. The theorem covers every state satisfying those conditions, although the runtime checks only the state actually encountered. It does not certify the whole page, missing archive resources, or visual fidelity. Browser execution, parsing, and the match between the formal semantics and JavaScript remain explicit trust assumptions.

**Differentiator — hypothesis.** FidEx says it works by “tracking and comparing the execution of scripts between when a page is crawled and when its copy is loaded.” This project would certify a supported rewrite before it executes, without needing a matching live execution at that moment. Translation validation already exists: [Kwon et al., “Translation validation for JIT compiler in the V8 JavaScript engine” (2024)](https://dl.acm.org/doi/abs/10.1145/3597503.3639189) is a close methodological comparison. The contribution must be archive-specific equivalence, sound runtime conditions, and useful coverage of real archive bugs. Applying a solver to a few synthetic rewrites would be insufficient.

**Group fit — judgment.** Harsha's archive work supplies the failure corpus, replay infrastructure, and a meaningful baseline. Your browser experience helps identify which rewrites and host operations actually matter. Arvin's verification experience could help keep the theorem and implementation aligned; Ramesh's systems perspective helps judge deployment cost. This is the strongest answer to “we have lots of data, we have lots of experience.”

**First paper — proposed 4–6 months, contingent on a short pilot.** In the first two weeks, classify roughly 30 available FidEx rewrite failures and determine whether a recurring family fits a small semantics. Build a checker in Lean or Rocq, using SMT for candidate obligations only if its answers are checked or clearly included in the trusted base; reuse FidEx's replay machinery. Prove checker soundness and runtime-condition validity for the selected fragment. Evaluate real fixed and faulty rewrites, held-out pages, rejection rates, page-level coverage, and added replay latency. Report unsupported cases separately from correct rewrites.

**Biggest risk and what failure teaches.** JavaScript's dynamic behavior may leave almost nothing useful certifiable. If the pilot cannot cover a recurring real failure family without modeling much of the browser, stop. The useful finding would be which missing state or browser semantics prevents local certification and whether the shared replay functions should be verified instead of individual rewrites. That finding alone is not automatically a paper.

2. “Can a browser prove that each credentialed request has current authorization when dispatched?”

**Problem and why now.** A browser agent's authorization can become stale across navigation, redirects, asynchronous work, and session reuse; the supplied review identifies a concrete contemporary failure, Lightpanda's advisory titled “Credential headers leak across cross-origin redirects.” [Lightpanda advisory](https://github.com/lightpanda-io/browser/security/advisories/GHSA-mcw6-8p83-pm3h). That motivates studying authorization at the actual send point rather than only when an agent issues a command.

**Exact verification target — proposal.** Implement a small request broker that owns API authorization tokens and enforces permissions granted by a trusted operator or application, which the browsing agent cannot expand. Permissions bind a session, document generation, destination origin, and permitted operation. A document generation changes when navigation replaces the document. Prove that every broker-authorized send uses the current permission, that redirects require a fresh decision for the new destination, that revocation and sending have a defined atomic ordering, and that session reuse cannot revive old permissions or release a previous session's credentials.

Illustrative failure: a document queues an authenticated API request, navigation revokes its permission, and the queued request later tries to run. A destination allowlist still permits that server; the broker rejects the expired document permission. Plain guarantee: a request can carry a broker-held credential only to its authorized destination with valid permission at dispatch. Dispatch means committing the request to the transport queue; checking and committing are one serialized operation relative to revocation. Revocation blocks later dispatches, but does not recall queued or transmitted bytes. Use separate renderer processes and enforce that their network traffic goes through the broker. The integration must establish this enforcement, not merely prove a function called `allow`. Ordinary passwords typed into page-visible DOM fields, permitted-site misuse, timing channels, and the agent's understanding of user intent are outside this first theorem.

**Differentiator — hypothesis.** A verified browser core is established prior work. [Quark, USENIX Security 2012](https://www.usenix.org/conference/usenixsecurity12/technical-sessions/presentation/jang) already claims “tab non-interference, cookie integrity and confidentiality, and address bar integrity.” Agent information-flow policies are also close competition: the supplied review describes [SPIDES](https://arxiv.org/abs/2610.24277) as using “site-supplied labels.” The proposed contribution is an executable proof covering the lifetime of an authorization through browser events and actual request dispatch, evaluated against those alternatives. “A verified policy layer for agents” alone is not a sufficient novelty claim.

**Group fit — judgment.** This uses browser behavior and real request traces, with a compact concurrent state machine that connects naturally to Arvin's ZENITH experience. Harsha and Ramesh's web measurement experience can establish whether the problematic event sequences occur in realistic workflows. Their recent LLM work motivates the workload, but does not by itself establish demand for this mechanism.

**First paper — proposed 4–6 months.** Build a Verus-verified Rust broker and connect it to Chromium through one controlled network path. Initially support navigation, fetch/XHR, and redirects; disable unsupported network paths such as WebSockets and service workers in this configuration. Start with broker-held authorization headers instead of attempting every cookie rule. Prove the broker's transitions and credential-selection code, and document the unverified browser adapter and OS enforcement assumptions. Evaluate historical redirect failures, deliberately raced navigation/revocation/reset cases, ordinary agent workflows, task completion, and latency. Compare with a static proxy allowlist and a check performed only when the agent invokes a tool.

**Biggest risk and what failure teaches.** A conventional proxy plus existing capability techniques might provide nearly all the benefit. First test whether document identity and permission lifetime prevent failures that destination filtering misses. If they do not, this is likely good engineering rather than a research contribution. If they do, the result identifies exactly which browser state an external proxy needs.

3. “Can checked JIT code make sharing an engine process defensible?”

**Problem and why now.** Sharing processes is already used in edge computing, but accepting generated native code creates a difficult isolation boundary: Cloudflare's hardening discussion assumes attackers cannot execute arbitrary machine code because “If they did, they could disable memory protection keys.” [Cloudflare security hardening](https://blog.cloudflare.com/safe-in-the-sandbox-security-hardening-for-cloudflare-workers/). The research question is whether a small verified checker can remove part of that assumption at acceptable cost.

**Exact verification target — proposal.** For one engine and one instruction set, prove that accepted JIT code can read and write only its assigned memory region, use only permitted control-flow targets, and enter host code only through specified interfaces. Also verify the installation and retirement protocol: checked code cannot change while executable, permissions cannot be changed by tenant code, and recycled code cannot retain authority from a previous tenant.

This is a theorem about accepted code and its lifecycle. A system-level isolation claim additionally requires confinement of the interpreter, GC, native builtins, and host bindings, plus correct host-call contracts. A checker cannot make those obligations disappear. V8 isolates and pointer compression alone do not establish them. Start by reusing a whole-engine sandbox design, and include its assumptions in the proof boundary. Treat architectural memory isolation separately from Spectre resistance; do not claim cross-tenant confidentiality while leaving speculative reads unaddressed.

**Differentiator — hypothesis, with substantial competition.** [Icarus, SOSP 2024](https://dl.acm.org/doi/abs/10.1145/3694715.3695949) provides JIT components “automatically, formally verified to be safe.” [Mohabi, OSDI 2026](https://www.usenix.org/conference/osdi26/presentation/sharma) says it uses software fault isolation “to ensure JavaScript engine bugs cannot affect the rest of the browser.” [LFI's verifier proof](https://arxiv.org/abs/2508.15898) already verifies that accepted programs “never read or write to memory outside of a designated sandbox region.” Consequently, neither checking machine code nor choosing a region per tenant is enough. The candidate contribution is support for a real JS JIT's changing code, host transitions, and tenant reuse, with a measured density benefit. The checker would establish confinement of generated code without assuming the generator emits correct code; the reused sandbox must confine the native engine itself. Whether existing systems already provide this combination is unresolved. Full-text and artifact comparison could eliminate this idea.

**Group fit — judgment.** This directly joins your browser experience with a systems cost question and Arvin's verification experience. The group's web workloads could supply a better evaluation than compiler microbenchmarks alone. The fit is weaker than the first two projects because machine-code confinement requires specialized expertise, and strong competing groups already work on it.

**First paper — proposed 6–9 months after a four-week feasibility gate.** First inspect Mohabi and LFI's artifacts, inventory one JIT tier's native exits, and measure proportional physical memory per completed session against separate processes. Continue only if an existing sandbox can cover native engine execution and a restricted tier can be checked without trusting its compiler. Reuse the existing verifier proof infrastructure; build code-lifecycle checks and selected host interfaces. Evaluate realistic JS workloads, adversarial generated code, fallback frequency, compilation latency, throughput, and memory at equal workload completion. A first paper can cover an edge-style JS runtime with a restricted host API; a full browser is a later step.

**Biggest risk and what failure teaches.** Native runtime paths or speculative execution may dominate the problem, or sandboxing and fallback may erase the savings. Failure would locate the actual cost and trust boundary rather than assuming “300 MB per tab” is removable process overhead. A negative result needs convincing measurements; an incomplete checker alone is not a paper.

Your open questions, directly:

“It needs to be something special, something ideally to do with the web, not just PL”

My judgment: make the web behavior essential to the theorem and evaluation. Archive rewrites depend on historical resources and browser-visible URLs. Request authorization depends on origins, redirects, document replacement, and sessions. The JIT project is more general runtime research unless real browser workloads and integration drive its design. The first two therefore satisfy this preference more naturally. The group's distinctive advantage is access to failures and deployment context that determines what should be proved.

“maybe we should do something about security with the agents using the browsers. Although that is also somewhat crowded”

Yes, but I would pursue a concrete browser-enforced property such as project 2. Assume page content can fully mislead the agent, then ask what operations the browser must still prevent. This makes the security condition precise. Quark and SPIDES make a generic isolation or information-flow pitch difficult; authorization lifetime is a candidate distinction to validate. Do not claim that correct request authorization prevents prompt injection or that it captures all user intentions.

“process isolation across browser tabs ... maybe that would be interesting for Cloudflare workers or something like that to share processes”

Yes, as an isolation-strength or cost project. Cloudflare already says it “can run many isolates within a single process” in its [security model](https://developers.cloudflare.com/workers/reference/security-model/), so sharing itself is established. A restricted edge runtime gives project 3 a smaller host interface than a browser. You need to establish what additional attacker capability the proof tolerates and what cost it saves at the same security target. Full JavaScript correctness is unnecessary, but the entire isolation boundary still needs justification.

“We could argue for agent infrastructure ... efficient browsers ... However, that just are used for light panda”

I take this to mean: does Lightpanda already cover the efficient-agent-browser story? My answer is that efficiency is the workload motivation, not the research contribution. Project 2 could establish a specific authorization guarantee in an existing browser; project 3 could establish a stronger isolation boundary per unit of memory. Measure both against existing implementations under comparable task completion and security assumptions. If Lightpanda already meets the actual requirement cheaply enough, that weakens the performance pitch; attaching a proof to unrelated policy code would not rescue it.

“I thought we are trying to find things we want to formally verify, right?”

Yes. The three objects are an archive-rewrite checker, a credentialed-request broker, and a JIT-code checker plus code-lifecycle protocol. Each needs a machine-checked statement about executable code or an explicit refinement link to that code. Measurements choose the target and establish usefulness; they do not replace verification. For runtime checking, the checker is proved sound once for all admissible inputs, then evaluates the concrete state encountered during execution. Merely observing that one run succeeded provides no such theorem.

“Not sure ... how we turn them into research projects that my advisors would like.”

I would bring the first two as concrete options and the third as a conditional bet. For each, show one real failure, one precisely stated guarantee, the closest existing system, and a two-to-four-week experiment that can reject the idea. Lead with project 1 because it extends a demonstrated group strength. Ask the advisors to choose the failure class and acceptable scope before committing to a browser, language, or whole-engine proof. My recommendation is to choose one pilot, not start three implementations.
