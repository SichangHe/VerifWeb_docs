Last week, I tried to find web problems that we want to formally verify. The requirements are: a differentiator, bite-sized problems, something actually breaks otherwise. The biggest problems is finding directions. I went through about 30 candidates and kept 3, which I detail below. I briefly mention discarded ideas at the end.

First, an agent browser core on [Servo](https://github.com/servo/servo). Running many users' sessions in one process is far cheaper than a process per tab, and agent browsers such as [Lightpanda](https://github.com/lightpanda-io/browser) already do it, but it is only safe if one session provably never sees another's data. We would prove that every network and storage access goes through a small verified core that enforces the URL, cookie and redirect rules per session, and perhaps verify the pertinent parts of the JS engine.

Regarding the checking JIT-generated code on the fly Harsha proposed. Checking generated code before running it has been done, but only for code compiled ahead of time into one sandbox ([RockSalt](https://doi.org/10.1145/2254064.2254111), [VeriWasm](https://www.ndss-symposium.org/wp-content/uploads/ndss2021_5B-3_24078_paper.pdf), [LFI](https://arxiv.org/abs/2508.15898)). For JITs, people have verified parts of the compiler once ([Icarus](https://dl.acm.org/doi/abs/10.1145/3694715.3695949)) or checked that each compilation is correct ([TurboTV](https://doi.org/10.1145/3597503.3639189)). Nobody checks that the code the JIT generates for one session cannot touch another session's memory when sessions share a process, which we need from the engine for the browser core.

Second, consistent sign-in/out across apps that share one SSO login. Getting randomly signed out seems common for SSO: in one web app, "two active tabs can randomly log someone out about every 15 minutes" ([chat-platform](https://github.com/johannesjahn/chat-platform/issues/650)), and in another, multiple tabs break when the login provider rotates refresh tokens ([soliplex](https://github.com/soliplex/frontend/issues/670)); a 2026 paper calls such concurrent refreshes "the default behaviour of retrying mobile clients and multi-tab browsers" ([NEBULA](https://arxiv.org/abs/2608.04115)). Not being consistently signed out is also common: after the login provider revoked access, "318 RPs continued accepting cookies 10 days after revocation" ([Ghasemisharif and Kanich, IEEE S&P 2022](https://par.nsf.gov/servlets/purl/10339713)). Getting randomly logged out is annoying, but the inconsistent sign-out is a security problem.

We would build our own login provider and apps in verified Rust and prove that you are signed out everywhere exactly when you sign out. I have not read all the closest prior work, but the main formal model of OpenID Connect leaves logout out ([Fett et al. 2017](https://arxiv.org/abs/1704.08539)).

Third, real-time collaborative editor sync. This would be like Google Doc/ Overleaf but formally verified. Merge rules for CRDTs already have proofs (e.g. [Gomes et al. 2017](https://arxiv.org/abs/1707.01747)), but the sync protocol that decides what each side still needs has none on real code, and Automerge and Loro have open bugs where sync loops ([#772](https://github.com/automerge/automerge/issues/772), [#1284](https://github.com/automerge/automerge/issues/1284)) or copies silently diverge ([#1215](https://github.com/loro-dev/loro/issues/1215), [#1040](https://github.com/loro-dev/loro/issues/1040)). We would prove in Verus that two replicas reporting "in sync" hold identical documents and that they reach that state if messages are eventually delivered, which also fills the gap left by our forked editor's verified merge logic, where sync was assumed.

Other directions I looked at are not ready to share or are discarded. These include cookie consent reuse, shared caches and CDN purging, verifying JS in web archive replay, checking third-party page scripts for attacks like prototype pollution, HTTP parser disagreements, HTTP/2 flow control, back/forward cache restoration, user click activation across processes in Servo, deciding when a page's JS changed too much to invalidate previous assumptions, isolating an agent's actions across sites, and, for cookie sharing, what's a domain.
