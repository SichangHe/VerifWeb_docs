Three coherent PhD stories emerge from your results and review audits. Each maps to a different piece of your advisors’ feedback: **Story 1** bets on the high-risk "for the given state / re-verify on the fly" differentiator, **Story 2** bets on "bite-sized problems and slow headway" in Rust engines where your strongest concrete bugs live, and **Story 3** turns "formal verification is done once and never touched again" into a thesis on continuous proof maintenance.

**Story 1: Snapshot-Guarded Verification of Live Web Scripts ("For the Given State")**

* **Thesis:** A browser can prove security properties of dynamic third-party scripts at page load by conditioning static proofs on a live DOM/heap snapshot and installing lightweight engine watchpoints that invalidate the proof—triggering fallback isolation or re-verification—the moment that state mutates.
* **Problem & why it matters:** Proving properties of arbitrary JavaScript for *all* states is intractable due to prototype mutation and dynamic aliasing, yet web scripts routinely access sensitive data (our crawl found 11/139 email-fill pages sending email hashes or raw values cross-domain before submit, 63/95 sites mutating built-ins after load, and only 3.19% of HTTP(S) cross-site script tags using Subresource Integrity).
* **Why new vs. prior work:** Our search found no system combining machine-checked script proofs, live heap snapshots, and runtime invalidation guards; prior work only builds pieces—JIT speculation/deopt without app-level proofs (V8 `compilation-dependencies.h`; Hackett & Guo, PLDI ’12; CoreJIT, POPL ’21), code-staged analysis without heap guards (Chugh et al., PLDI ’09), static-spec Java monitors (StaRVOOrS, RV ’15), or unguarded snapshot-seeded analysis (HeapDL, OOPSLA ’17; Dynamic Determinacy, PLDI ’13, whose facts hold for *all* runs).
* **Supporting vs. missing/weak results:** Supported by web crawl data (prototype mutations across 46/120 npm package versions and 63/95 sites; cross-domain email flows) and a sound 24-obligation Verus model of realm write-barrier isolation (`tabiso_verus/heap.rs`). **Weaknesses:** Our prototype JS symbolic executor is **unsound** (ignores `ReferenceError`/`TypeError`, treats numbers as unbounded integers, mislabels `NaN` as an exception, and cannot parse real scripts), our worker-memory benchmark accidentally measured 50 *exited* workers rather than live browser isolates, and no guard or fallback exists yet.
* **First 3 concrete steps:** (1) Replace the unsound toy AST checker with a sound symbolic check over a tiny bytecode subset (e.g., Boa bytecode) with IEEE-754/fixed-width semantics; (2) hook Boa or V8 property/map watchpoints to invalidate a toy "no `document.cookie` read" proof when globals or `Object.prototype` mutate; (3) replay the 95-site crawl traces to measure how often real pages trip those guards.
* **Biggest risk:** Real sites mutate shared prototypes so aggressively (63/95 sites) that watchpoints may invalidate almost immediately on load, causing constant fallback/re-verification overhead that erases the value of proving the initial snapshot.

**Story 2: Spec-Driven Modular Verification of Rust Browser & JS Engines ("Bite-Sized Headway")**

* **Thesis:** Mechanically translating algorithmic web and ECMAScript specifications into Verus contracts—paired with mutation audits—exposes machine-arithmetic and callback-reentrancy bugs across production Rust browser engines (Boa, Nova, Servo) that standard conformance suites (`test262`, WPT) systematically miss.
* **Problem & why it matters:** Writing browser components in safe Rust prevents raw memory corruption in safe code, but engines still panic or silently violate specs when translating unbounded spec math (`ToIntegerOrInfinity`) into fixed-width integers (`f64 as i64`) or when user callbacks (`valueOf`, getters) shrink backing buffers mid-operation.
* **Why new vs. prior work:** Prior engine verification targets narrow C++/Wasm JIT passes via SMT—Firefox range routines (VeRA, PLDI ’20), loop-free V8 compilation validation (TurboTV, ICSE ’24), SpiderMonkey CacheIR stubs (Icarus, SOSP ’24), or Cranelift ISLE rule chains (Crocus/VeriISLE, ASPLOS ’24 & OOPSLA ’25)—whereas verifying Rust JS builtins and web parsers against mechanized ECMA-262 (ESMeta) and WHATWG algorithms in Verus is unexplored.
* **Supporting vs. missing/weak results:** Strongest empirical footing: found **confirmed, reproducible bugs on current `main` builds** missed by `test262`, including Boa `String.prototype.at(-1e300)` panics and `Array.prototype.at(-1e300)` wrong lookups, Boa and Nova `f64 as i64` saturation bugs (`ToInt8`/`ToUint16`/`ToInt32`), callback buffer-shrink panics in Boa (`ArrayBuffer.slice`, `Atomics.store`/`add`, `setFromBase64`) and Nova (`TypedArray.copyWithin`), Nova non-base-10 `toString(radix)` exponents, Servo `Blob.slice` i64 overflow, and `cranelift-bitset` `from_range(64,64)`. **Weaknesses:** Every Verus proof so far checks a **hand-written model**, not upstream crates (`JsValue`, `Context`, `Cell`, and raw pointers are unmodeled); several early proofs had weak contracts that accepted broken mutants (e.g., our verified `Blob.slice` saturating fix still computes start index `1` instead of `7` on `slice(2,8).slice(-1)`); and several URL/Boa bugs (`rust-url` #1159/#1123/#1113, Boa `toPrecision` #5225) were already known upstream.
* **First 3 concrete steps:** (1) Upgrade the host from Java 11 to Java 17 to build ESMeta and auto-generate Verus `spec fn`s from ECMA-262 IR instead of hand-transcribing prose; (2) build a reusable Verus state model for callback reentrancy (resizable `ArrayBuffer` + `ToIntegerOrInfinity` bounds) to verify all Boa/Nova `TypedArray` and `Atomics` builtins; (3) require every Verus spec to kill held-out bug mutants so weak contracts (like the `Blob.slice` survivor) are caught immediately.
* **Biggest risk:** If you cannot bridge Verus to actual in-tree Boa/Servo types (`JsValue`, GC handles, interior mutability), committees may view this as a collection of disconnected model-assisted bug hunts rather than a unified systems thesis.

**Story 3: Continuous Proof Maintenance & Spec-Drift Auditing Across Browser Commits ("Never Touch It Again")**

* **Thesis:** Formal verification can be kept alive across daily browser commits by combining regression-guided precondition auditing, real-bug mutation testing, and automated LLM-assisted proof repair to detect when code changes break proofs or silently drift outside a proof’s domain.
* **Problem & why it matters:** In fast-moving systems like Servo, Boa, and Wasmtime, one-shot formal proofs either break on routine commits or silently rot because their preconditions exclude the exact boundary inputs developers later fix—making static verification too brittle for continuous integration.
* **Why new vs. prior work:** State-of-the-art Verus systems (Anvil; Atmosphere at ~6K executable LoC) and browser verifiers (VeRA, Crocus) verify a single code snapshot, while synthetic mutation benchmarks (MutDafny, VeriContest) and algorithmic TLA-Verus translations (38% on 809 liveness benchmarks without implementation refinement) do not address proof evolution and domain drift across real browser bug-fix commits.
* **Supporting vs. missing/weak results:** Supported by 48 distinct passing Verus proof files, a 4/4 model kill rate on historical bug/fix pairs (`cranelift-bitset`, Boa microtask ordering, V8 CVE-2020-6418, Wasmtime CVE-2023-26489), and an eye-opening commit-retargeting result (`vlm6_repair`): replaying `smallbitvec` overflow fix `b17ba46 → 5d195c9` needed **zero proof repair** only because the proof’s precondition (`cap <= 64 * 1000000`) excluded the `usize::MAX` inputs that the commit actually fixed. **Weaknesses:** We have **zero examples of actual broken-proof repair** yet (`smallbitvec` was out-of-domain; `cranelift-bitset` was unchanged code), the 4/4 mutant kills used contracts written *after* knowing the bugs, and our proof audit (`cx_proofs`) found 14 probes where weak contracts accepted wrong functional behavior (plus an unsound `ptr::add` contract in early `smallbitvec` that proved `assert(false)` before repair).
* **First 3 concrete steps:** (1) Curate a held-out benchmark of 15–20 real git bug-fix commits across Boa, Nova, and Servo where the commit's regression test input is forced to satisfy the Verus precondition; (2) measure how often frozen pre-commit contracts fail to reject the buggy parent (spec weakness) vs. how often feature commits break valid proofs (repair cost); (3) build an agent loop that uses regression tests and diff-mutants to automatically strengthen weak contracts and repair broken proofs across git history.
* **Biggest risk:** Because Verus currently requires rewritten models for complex Rust crates, translating upstream git diffs into model diffs by hand could contaminate the evaluation unless you verify in-tree code slices directly.

**How to combine them for your advisors:** Pitch **Story 2 as your foundation** (it gives immediate, bite-sized bug-finding and proof wins in Boa/Nova/Servo) and either **Story 3** (evolving those specs across commits) or **Story 1** (using Boa's verified builtins + watchpoints to guard live page snapshots) as the **differentiator** once the base models are solid.
