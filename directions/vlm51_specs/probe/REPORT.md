Feasibility probe: does a small hand model of the WHATWG navigation spec rediscover whatwg/html#12861?

Answer. FACT: yes. A 15-state Python BFS model (model.py, ~70 lines of model code, run output in run.txt) found two terminal states where the iframe load never fires. Trace B is the exact #12861 trace: fragment nav queues "finalize a same-document navigation"; location.search sets ongoing navigation := nav2; the queued apply-the-history-step sets ongoing := "traversal"; navigate's in-parallel check sees "ongoing navigation is no longer navigationId" and aborts; ongoing returns to null; no load. Trace A is a sibling: the traversal-queue step runs first, and navigate's 'If navigable's ongoing navigation is "traversal" ... Return.' silently drops nav2. That second interleaving was also mentioned by farre in the issue thread ("which makes you bail in step 19 of #navigate, perhaps"), so it is not new. INFERENCE: neither trace is novel; the probe shows that rediscovery is cheap, not that discovery is.

Cost. FACT: about 30 minutes wall time, including reading the issue and the spec text (multipage browsing-the-web.html fetched 2026-11-13). The model encodes 6 spec steps: navigate's fragment branch, the "traversal" early return, "Set the ongoing navigation to navigationId", the in-parallel "no longer navigationId" abort, apply-the-history-step's 'ongoing := "traversal"' and its same-document 'ongoing := null'. "Navigate to a fragment"'s append and finalize-same-document's active-entry guard appear as comments that justify one transition each. Each action cites its spec step in a comment.

Mechanical vs judgment. INFERENCE: the per-step transitions were mechanical once chosen, because each spec sentence that reads or writes "ongoing navigation" became one guarded assignment. The judgment calls carried the result. (1) I chose which variable and steps to include, guided by the issue; without the issue I would have had to model every writer of ongoing navigation, which grep finds (about 8 sites). (2) I chose atomicity: I let other threads run between apply-the-history-step's set to "traversal" and its reset to null, justified by its "wait for completedChangeJobs" loop. (3) I collapsed everything after the fetch into "load fires". (4) I chose the property: every terminal state has load fired, or the nav failed observably. A silent "Return" counts as a failure here, which is debatable because a WebDriver BiDi "canceled" status is emitted. (5) I assumed, as the issue states, that the iframe is a changing navigable for the update-only step. OPINION: all of this was easy because the issue had already told me where to look. A blind model would need the whole navigate/apply-history-step state machine, likely 10x more work.

Reuse for #12961 / #12362. INFERENCE: the same skeleton (threads S/Q/P plus the traversal queue) carries over, but the state does not. #12961 needs session history entry lists, the current step, a retained target entry in the continuation, and the replaceState/pushState sync path. Its property is a safety invariant: the active entry is in the navigable's entry list, and the navigation API current index is not -1. That is an estimated 2-4x this model. #12362 needs the navigation API's "ongoing navigate event", intercepted traverse, and deferred "resume applying the traverse history step". Its property is "resumed steps observe their own navigate event". Both are of the same kind (a queue-jumping or deferred step races on shared per-navigable state), and an explicit-state checker handles them. I did not build either.

Limits. FACT: I did not run TLA+ because Python was enough at this size. Spec step numbers (8.4, 14.10.1, 19, 20, 24.2) are as cited in the issue. I did not re-derive them from the spec numbering, but I did match the sentence text. The model covers one WPT test, with one iframe and two navigations.
