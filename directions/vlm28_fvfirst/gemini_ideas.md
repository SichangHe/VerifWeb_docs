To find formal-verification-first (FV-first) web directions that satisfy systems and networking advisors, start from the properties that **only deductive proofs can establish**—because their falsification requires reasoning over infinite execution traces (liveness), pairs of traces or programs (relational 2-safety), combinatorial interleavings of concurrent events, or universal quantification over structured inputs where bug-triggering states have measure zero under random fuzzing. Each capability below is mapped to a self-contained Rust web crate or browser subsystem where unverified code (and even informal developer proofs in source comments) failed in documented vulnerabilities.

### 10 Formal-Verification-First Web Research Directions

**Direction 1 — [Liveness under Fairness + Linear Resource Conservation] Cross-Layer Flow-Control Credit Conservation and Starvation Freedom in Async HTTP/2 Proxies (`pingora` + `h2`)**

1. **Exact statement to prove:** For every sequence of downstream and upstream HTTP/2 frames and stream cancellations (`RST_STREAM`), if the upstream connection eventually drains or times out under weak fairness, every byte of connection-level flow-control credit allocated to a cancelled downstream stream is eventually returned via `WINDOW_UPDATE`, and no active stream with an unblocked upstream is permanently starved of connection-window credit.
2. **Why only a proof settles it:** Safety invariants on flow-control counters never fail during this bug (no counter overflows, underflows, or panics); the bug is an infinite-trace liveness deadlock where linear credit tokens remain pinned inside an unpolled `tokio::select!` branch. Fuzzing and finite-duration testing cannot distinguish a slow upstream from permanent credit starvation.
3. **FV contribution:** Combining Verus linear `tracked` ghost tokens (for exact conservation of flow-control window capacity across reference-counted handles) with TLA-style temporal liveness reasoning over asynchronous Rust `Future` polling schedules.
4. **Web system + real bug:** Cloudflare `pingora` v0.8.0 and Rust `h2` v0.4.x (`cloudflare/pingora` Issue #910, 2026, [https://github.com/cloudflare/pingora/issues/910](https://github.com/cloudflare/pingora/issues/910)), where reporter `molocule` writes verbatim: `"When proxying a downstream HTTP/2 connection to an upstream HTTP/2 connection, a downstream RST_STREAM is not acknowledged by pingora if it arrives while the proxy is blocked writing the request body to the upstream (parked on upstream flow control). The proxy task holds the downstream stream handles until the upstream write completes (which can be forever for stalled upstreams as there is no default write_timeout ). Because of how the h2 crate accounts for flow control, the cancelled stream's connection-window credit is never returned while those handles are held. Each such stream becomes a 'zombie': closed at the protocol level, but still pinning its share of the shared downstream connection window."` and `"Flow-control accounting remains perfectly consistent on both ends — which is why nothing errors. New requests stall mid-upload waiting for window that will never be granted, with no signal that would let the client route around the problem: the connection is not dead, just silently unusable, and every cancelled-while-blocked stream shrinks the usable window further."`
5. **Tool:** Verus (linear ghost tokens + Anvil-style temporal TLA embedding).
6. **Closest prior FV work:** *Anvil: Verifying Liveness of Cluster Management Controllers* (OSDI 2024, [https://www.usenix.org/system/files/osdi24-sun-xudong.pdf](https://www.usenix.org/system/files/osdi24-sun-xudong.pdf)), where Xudong Sun et al. write verbatim: `"Verus does not support temporal logic reasoning, so Anvil provides a TLA embedding on top of first-order logic (§4.2) to enable TLA-style temporal reasoning."`

**Direction 2 — [Universal Inductive Invariants over Unbounded Protocol Inputs] Quantitative Queue-Bound and Amplification-Freedom Proofs in Sans-IO QUIC (`quinn-proto`)**

1. **Exact statement to prove:** For every reachable state of the `quinn-proto` connection state machine and any sequence of incoming QUIC frames (including out-of-order `NEW_CONNECTION_ID` frames with arbitrary 62-bit `sequence` and `retire_prior_to` offsets while peer `ACK` frames are withheld), the length of every outbound control queue (`pending.retire_cids`) is bounded by a constant $K$ unless the connection immediately transitions to a terminal transport error.
2. **Why only a proof settles it:** Reaching the bug requires a two-step state transition (jumping the sliding window offset via a large `retire_prior_to`, then flooding sequence numbers below the offset while withholding `ACK`s to block queue draining). Notably, the `quinn-proto` developers wrote an informal safety proof in a code comment claiming lazy retirement prevented unbounded buffering—and their own informal proof missed the exact `Err(InsertError::Retired)` code path that lacked the cap.
3. **FV contribution:** Mechanized quantitative resource-bound invariants in Verus across multi-module sans-IO transport state machines, proving worst-case memory amplification bounds ($O(1)$ queue growth per unacknowledged frame window) over all valid and invalid frame sequences.
4. **Web system + real bug:** Rust `quinn-proto` (`quinn-rs/quinn` Security Advisory GHSA-hmxj-32vh-65vr, 2026, [https://github.com/quinn-rs/quinn/security/advisories/GHSA-hmxj-32vh-65vr](https://github.com/quinn-rs/quinn/security/advisories/GHSA-hmxj-32vh-65vr)), where the maintainers write verbatim: `"A single NEW_CONNECTION_ID{sequence=N, retire_prior_to=N} with large N moves offset to N , but the returned retired range is clamped to LEN (5), so the Ok(Some) cap check trivially passes. Net effect: the window offset is now N , yet almost nothing was buffered. The comment at lines 79–81 is the vulnerability's own disproof. It argues we can't be made to buffer unboundedly because the gap CIDs are retired lazily — 'we'll retire it then.' But 'then' is the Err(Retired) arm above, and that arm is the one without the cap. The lazy path the comment relies on for safety is precisely the unbounded path."` (Related control-frame exhaustion flaws also hit the Rust `h2` crate in RUSTSEC-2023-0034 in 2023, RUSTSEC-2024-0332 in 2024, and RUSTSEC-2026-0258 in 2026 at [https://rustsec.org/packages/h2.html](https://rustsec.org/packages/h2.html).)
5. **Tool:** Verus.
6. **Closest prior FV work:** *Formal Specification and Testing of QUIC* (SIGCOMM 2019, [https://www.mcmil.net/pubs/SIGCOMM19.pdf](https://www.mcmil.net/pubs/SIGCOMM19.pdf)), where Kenneth L. McMillan and Lenore D. Zuck write verbatim: `"We develop a formal specification of QUIC based on the draft standards documents, and refine it by applying specification-based testing to the implementations."`

**Direction 3 — [Concurrent Refinement & Cancellation Safety] Multiplexed IPC Subchannel Lifecycle and Timeout-Cancellation Safety in Servo (`servo/ipc-channel`)**

1. **Exact statement to prove:** Every OS pipe receiver and multiplexed subchannel in Servo's `ipc-channel` and `ipc-channel-mux` crates satisfies lossless, FIFO-ordered message delivery and exact file-descriptor/subsender reclamation under arbitrary concurrent subsender transmissions, subchannel drops, and OS async-read timeout cancellations.
2. **Why only a proof settles it:** When a timeout expires concurrently with an OS kernel pipe read (`ReadFile` / `CancelIoEx`), or when multiplexed subchannels close while in-flight subsenders are being transferred across processes, the race window is microseconds wide and depends on OS scheduler interleavings. Servo developers normally test in single-process mode, leaving multi-process IPC cancellation and subchannel drop corners unreachable by standard integration tests.
3. **FV contribution:** Concurrent state-machine refinement in Verus (`VerusSync`) that models asynchronous OS I/O completion vs. cancellation states alongside distributed reference-counting protocols for multiplexed IPC channels.
4. **Web system + real bug:** Servo's `ipc-channel` (`servo/ipc-channel` Issue #450, 2026, [https://github.com/servo/ipc-channel/issues/450](https://github.com/servo/ipc-channel/issues/450), and Issue #396, 2025, [https://github.com/servo/ipc-channel/issues/396](https://github.com/servo/ipc-channel/issues/396)). In Issue #450, the bug report states verbatim: `"On Windows, OsIpcReceiver::try_recv_timeout can silently discard data that the kernel has already read from the pipe. This happens when a timeout and a completed read race in MessageReader::issue_async_cancel ."` and `"Because the pipe is in byte mode, the bytes consumed by the kernel's ReadFile are removed from the pipe. Since the buffer length is not updated, those bytes become permanently inaccessible. The next call to start_read overwrites them in the buffer."` In Issue #396, Servo contributor `glyn` writes verbatim: `"Handling all the corner cases and avoiding race conditions related to closing subchannels while transfers are in progress. (If it's anything to go by, RPC cancellation is probably the darkest corner of the Hurd design.1)"` and `"It seems that many Servo developers prefer to run Servo in single process mode, so IPC does not get the level of testing it would do otherwise and this may make it risky to 'bed in' multiplexing."`
5. **Tool:** Verus (`VerusSync` tokenized state machines).
6. **Closest prior FV work:** *Verus: A Practical Foundation for Systems Verification* (SOSP 2024, [https://www.chajed.io/papers/verus:sosp2024.pdf](https://www.chajed.io/papers/verus:sosp2024.pdf)), where Andrea Lattuada et al. write verbatim: `"Describe VerusSync, Verus's new approach to allowing the developer to reason about concurrent execution at the level of the application, rather than the low-level mathematical objects required by prior work [3, 29, 30]"`

**Direction 4 — [Relational 2-Safety Across Two Programs + Verified Parsers] Proxy-to-Origin HTTP Framing and Path-Canonicalization Equivalence (`pingora` / `hyper` / Envoy)**

1. **Exact statement to prove:** For every input byte stream $b$, if a reverse proxy's parser and path normalizer $P_{\text{proxy}}(b)$ accepts $b$ and emits canonicalized wire bytes $b'$, then any RFC-compliant origin parser $P_{\text{origin}}(b')$ parses $b'$ into the identical message boundaries, target URI path segments, and header map: $\forall b.\; \text{accept}(P_{\text{proxy}}, b) \implies \text{semantic}(P_{\text{origin}}(\text{serialize}(P_{\text{proxy}}(b)))) = \text{semantic}(P_{\text{proxy}}(b))$.
2. **Why only a proof settles it:** Request smuggling and path-confusion authorization bypasses are relational properties of *two distinct parsers* over all possible byte streams. Differential grammar fuzzers (such as T-Reqs) sample finite mutations and miss syntax corners (like semicolon path parameters `/..;foo=bar/admin` or conflicting `Transfer-Encoding` / `Content-Length` headers); only a relational equivalence proof guarantees zero proxy-origin desynchronization across all inputs.
3. **FV contribution:** Relational translation validation and cross-parser bi-simulation in Verus, extending single-parser non-malleability combinators (`Vest`) to prove semantic equivalence between an edge proxy's normalizer-serializer pipeline and a backend HTTP parser.
4. **Web system + real bug:** Rust `hyper` CVE-2021-21299 / RUSTSEC-2021-0020 (2021, [https://advisories.gitlab.com/cargo/hyper/CVE-2021-21299/](https://advisories.gitlab.com/cargo/hyper/CVE-2021-21299/)), which states verbatim: `"This combined with an upstream HTTP proxy that understands the request payload boundary differently can result in “request smuggling” or “desync attacks”."`; and Envoy Proxy CVE-2026-73551 (2026, [https://www.sentinelone.com/vulnerability-database/cve-2026-73551/](https://www.sentinelone.com/vulnerability-database/cve-2026-73551/)), where SentinelOne's vulnerability database entry states verbatim: `"Envoy's path canonicalization does not recognize dot (.) and dot-dot (..) segments when they carry semicolon path parameters. A request such as /user/..;foo=bar/admin is not collapsed to /admin even when path normalization is enabled."` and `"The upstream then interprets /user/..;foo=bar/admin as /admin. This split interpretation between proxy and origin is the classic definition of a path confusion vulnerability and produces an authorization bypass whenever Envoy is the enforcement point."`
5. **Tool:** Verus (extending `Vest` parser/serializer combinators).
6. **Closest prior FV work:** *Vest: Verified, Secure, High-Performance Parsing and Serialization for Rust* (USENIX Security 2025, [https://www.usenix.org/conference/usenixsecurity25/presentation/cai-yi](https://www.usenix.org/conference/usenixsecurity25/presentation/cai-yi)), where Yi Cai et al. write verbatim: `"We show that Vest has executable performance on-par (or better) than hand-written, unverified parsers and serializers, and has orders of magnitude better verification performance relative to comparable prior work."`

**Direction 5 — [Set-Algebraic Inclusion Proofs over Infinite String Languages] Domain Subtree and Wildcard Language Inclusion in WebPKI & WebAuthn (`rustls-webpki` / `webauthn-rs`)**

1. **Exact statement to prove:** A TLS certificate validator or WebAuthn Relying Party accepts a candidate origin or wildcard DNS pattern $P$ against a permitted domain constraint $C$ if and only if the infinite set of hostnames generated by $P$ is a subset of the permitted domain subtree of $C$: $\forall P, C.\; \text{matches}(P, C) = \text{true} \iff \mathcal{L}(P) \subseteq \text{Subtree}(C)$.
2. **Why only a proof settles it:** Developers repeatedly implement domain constraint checks as point-wise pattern matching (checking whether `*.example.com` matches `accept.example.com`, which tests $\mathcal{L}(P) \cap \text{Subtree}(C) \neq \emptyset$ instead of $\mathcal{L}(P) \subseteq \text{Subtree}(C)$) or raw string suffix checks (`ends_with`). Unit tests with example domains pass while the logical quantifier is inverted.
3. **FV contribution:** Mechanizing DNS label trees, wildcard expansions, and WebAuthn RP ID origin rules as a decidable set algebra in Verus, proving that zero-copy Rust string matchers in `rustls-webpki` and `webauthn-rs` refine language inclusion ($\subseteq$) rather than intersection ($\cap$).
4. **Web system + real bug:** Both `rustls-webpki` CVE-2026-93601 / GHSA-xgp8-3hg3-c2mh (2026, [https://www.sentinelone.com/vulnerability-database/cve-2026-93601/](https://www.sentinelone.com/vulnerability-database/cve-2026-93601/)) and Kanidm's `webauthn-rs-core` GHSA-22w3-693w-x895 (2026, [https://github.com/advisories/GHSA-22w3-693w-x895](https://github.com/advisories/GHSA-22w3-693w-x895)). For `rustls-webpki`, the CVE-2026-93601 report states verbatim: `"A permitted subtree such as accept.example.com was treated as satisfied by a certificate asserting *. example.com, even though that wildcard could match names outside the permitted subtree, such as reject.example.com."` and `"The correct behavior is to reject any wildcard whose expansion set includes names not covered by the permitted subtree."` For `webauthn-rs-core`, GHSA-22w3-693w-x895 states verbatim: `"This check is flawed, and could allow requests from an attacker-controlled domain such as hermit-crab. example to be accepted for the RP ID crab. example (assuming . example was publicly-registerable TLD) when the RP allows authenticating from a subdomain (disabled by default in webauthn-rs-core and webauthn-rs )."`
5. **Tool:** Verus.
6. **Closest prior FV work:** *Towards Practical, End-to-End Formally Verified X.509 Certificate Validators with Verdict* (USENIX Security 2025, [https://www.andrew.cmu.edu/user/bparno/papers/verdict-x509.pdf](https://www.andrew.cmu.edu/user/bparno/papers/verdict-x509.pdf)), where Zhengyao Lin et al. write verbatim: `"In this work, we present Verdict, the first end-to-end formally verified X.509 certificate validator with customizable validation policies. Verdict's formal guarantees cover certificate parsing, path building, and path validation."`

**Direction 6 — [Commutativity + Causal Authorization Refinement] Authorized Strong Eventual Consistency and Wire-Bound Safety in Collaborative/Federated Web State Resolution (extending TeamTypeV / Matrix)**

1. **Exact statement to prove:** For any causal DAG of collaborative or federated web events combining document edits with dynamic access-control (power-level) revocations, (a) any two honest replicas receiving the same set of events converge to the identical state, (b) no operation takes effect unless its author was authorized at its causal frontier, and (c) every accepted state transition preserves canonical wire-serialization bounds (such as canonical JSON `[-(2^53)+1, (2^53)-1]` integer limits).
2. **Why only a proof settles it:** In decentralized web collaboration (OT/CRDTs like TeamTypeV and federated DAGs like Matrix State Resolution), edits and permission revocations arrive concurrently across partitions and do not commute natively, while state-resolution tie-breakers and wire-serialization bounds interact across 64-bit vs. 53-bit integer limits. Random schedule testing cannot exhaustively cover the factorial space of causal DAG merge permutations.
3. **FV contribution:** Extending the student's Verus-verified OT engine (TeamTypeV) from pure text convergence to *Authorized Eventual Consistency*—proving convergence, causal authorization enforcement, and wire-serializer range refinement across non-commutative edit + ACL lattices using agent-driven Verus proofs.
4. **Web system + real bug:** Matrix Synapse CVE-2025-30355 (2025, [https://nvd.nist.gov/vuln/detail/CVE-2025-30355](https://nvd.nist.gov/vuln/detail/CVE-2025-30355) and [https://www.sentinelone.com/vulnerability-database/cve-2025-30355/](https://www.sentinelone.com/vulnerability-database/cve-2025-30355/)), where the NVD advisory states verbatim: `"Synapse is an open source Matrix homeserver implementation. **Direction 7 — [Mechanizing Prose Standards + Agent-Driven Proof Maintenance] Spec-to-Code Co-Evolution and Invariant Repair for Living Web Standards (`rust-url` / `idna`)**

1. **Exact statement to prove:** Across revisions of the Unicode UTS #46 and WHATWG URL living standards and corresponding commits in `rust-url` / `idna`, (a) the mechanized specification satisfies algebraic domain-uniqueness invariants (Punycode `xn--` decoding is injective and never accepts all-ASCII decoded labels, and `to_ascii` is idempotent), and (b) the Rust implementation refines the mechanized spec with proofs automatically repaired across spec and code diffs.
2. **Why only a proof settles it:** Conformance test suites (such as Web Platform Tests and Unicode test vectors) only check that code matches the prose standard; when the prose standard itself has a logic flaw, faithful implementations inherit the vulnerability. Only proving high-level algebraic security invariants (like canonicalization uniqueness for same-origin checks) against a mechanized spec catches flaws in the standard itself, and only automated proof repair keeps up with living-standard commits.
3. **FV contribution:** Combining prose-standard mechanization with counterexample-guided LLM proof repair in Verus (building on AutoVerus/ExVerus) to automatically localize and repair broken loop invariants and lemmas when a living web standard or Rust crate updates.
4. **Web system + real bug:** Rust `idna` and `url` crates (`rust-url`, used by Servo) CVE-2024-12224 / RUSTSEC-2024-0421 / GHSA-h97m-ww89-6jmq (2024, [https://rustsec.org/advisories/RUSTSEC-2024-0421.html](https://rustsec.org/advisories/RUSTSEC-2024-0421.html)), where the RustSec advisory states verbatim: `"idna accepts Punycode labels that do not produce any non-ASCII when decoded."` and `"This issue resulted from idna 0.5. 0 and earlier implementing the UTS 46 specification literally on this point and the specification having this bug. **Direction 8 — [Verified Policy Compilation & Adapter Monotonicity] End-to-End Semantic Preservation Across HTTP Header Adapters and Edge Authorization Engines (Envoy RBAC / Rust `cedar`)**

1. **Exact statement to prove:** For every HTTP request with arbitrary multi-valued headers and any authorization policy containing `Deny`/`Forbid` rules, the composition of the HTTP header-extraction adapter and the policy evaluator satisfies header-injection monotonicity: appending an additional untrusted header value to an existing header name can never flip a `Deny` decision to `Allow`.
2. **Why only a proof settles it:** Formally verifying an authorization engine in isolation (as AWS did for Cedar in Lean) leaves the *HTTP adapter boundary* unverified. When an adapter flattens multi-valued HTTP headers into a comma-concatenated string before invoking the policy engine, an attacker can inject a second header to evade exact-match `Deny` rules. Testing individual policies misses the relational property over all header-list mutations.
3. **FV contribution:** Relational monotonicity verification (2-safety privilege non-amplification under input extension) across the boundary between concrete Rust HTTP header maps (`http::HeaderMap` in Hyper/Pingora) and verified policy evaluators (`cedar-policy`).
4. **Web system + real bug:** Envoy RBAC Filter CVE-2026-26308 (2026, [https://nvd.nist.gov/vuln/detail/CVE-2026-26308](https://nvd.nist.gov/vuln/detail/CVE-2026-26308)), where the NVD entry states verbatim: `"Instead of validating each header value individually, Envoy concatenates all values into a single comma-separated string. 5. **Tool:** Verus (or Lean 4 composed with Verus for the Rust HTTP-to-Cedar adapter).

**Direction 10 — [Information-Flow Protocol Verification + Time-Consistent State Machines] Multi-Phase Handshake Monotonicity and Unlinkable Token Redemption in Web Transport & Privacy Protocols (`libp2p-quic` / Privacy Pass / OHTTP)**

1. **Exact statement to prove:** Across multi-phase cryptographic transport and web-privacy state machines in Rust: (a) post-handshake upgrade validation is monotonic with respect to wall-clock time progression $t_1 \le t_2$ and never panics on delayed TLS/QUIC fragments, and (b) in IETF Privacy Pass / Oblivious HTTP (OHTTP) Rust implementations, concurrent token redemptions satisfy linear single-use conservation (no double-spend) and information-flow unlinkability between issuance and redemption.
2. **Why only a proof settles it:** Time-of-check-to-time-of-use (TOCTOU) bugs across multi-phase handshakes require an adversary to stall a final packet until the exact millisecond a certificate expires between phase 1 and phase 2, which random network testing misses; similarly, unlinkability and injective single-use token redemption are relational/linear properties across all adversarial concurrency schedules.
3. **FV contribution:** Directly addressing the open problem identified by the Owl authors—extending Owl/OwlC (which compiles security protocols to Verus-verified Rust) with linear typing for injective single-use token redemption, control-flow refinement for unlinkability, and monotonic wall-clock time indices.
4. **Web system + real bug:** Rust `libp2p-quic` / `quinn-proto` CVE-2026-61544 / GHSA-5hq8-qhww-jm7q (2026, [https://www.sentinelone.com/vulnerability-database/cve-2026-61544/](https://www.sentinelone.com/vulnerability-database/cve-2026-61544/)), which states verbatim: `"When the post-handshake upgrade re-validates the certificate, wall-clock evaluation now returns an expiration error. 1. **Exact statement to prove:** Under weak fairness of async task scheduling and arbitrary downstream `RST_STREAM` cancellations or stalled upstreams, every unconsumed byte of connection-level flow-control credit held by a terminated stream is eventually returned to the shared connection window, and active streams never starve waiting on leaked window credit.
