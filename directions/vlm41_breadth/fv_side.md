# Formal verification of distributed and web systems: what worked at scale, what is left
(authored by agents unless marked 🧑)

Labels: FACT = quoted from a source I read. INFERENCE = my reasoning from facts. OPINION = my judgment. Quotes are verbatim; "[...]" marks my cuts. Where a source gave a DOI/arXiv/USENIX link I give it; otherwise I give the local file in /hdd1/sichanghe/paper_collection.

Scope limits, stated up front. (1) Google Scholar was used through the human's browser (queries in scholar/, 16 done). Scholar then raised a CAPTCHA; I did not touch it, so five planned queries were not run (trace validation, modular network verification, liveness gaps, specification gap, Google). (2) I found no Google distributed-systems verification paper in the queries that ran. I do not know of Google's practice from sources I read; I leave it blank rather than guess. (3) Meta: I found one verification paper (microkernel queues), nothing on Meta distributed systems. (4) Three ACM papers are blocked by Cloudflare for scripted download; I did not bypass it. ## 1. Takeaway

INFERENCE. Industry has verified, at scale, four kinds of thing: (a) protocol designs, by model checking in TLA+/P (AWS, Azure); (b) fixed-semantics languages and libraries with an SMT or proof-assistant model (Zelkova, Cedar, s2n, Kani on Rust); (c) network configuration, by analysis tools (Batfish, Azure); (d) implementations of one node, by lightweight methods that find bugs but do not prove absence (ShardStore, Coyote). Nobody in my sources has proved an industrial multi-node distributed system's implementation correct end to end. The links that stay open in every source are: design to code, safety to liveness, one node to many, and "is the trusted spec right".

## 2. Industry

### AWS

TLA+ for design (2014). FACT, Newcombe et al., AWS tech report, 2014, https://6826.csail.mit.edu/2019/papers/formal-methods-amazon.pdf: "So far we have used TLA+ on 10 large complex real-world systems. In every case TLA+ has added significant value, either finding subtle bugs that we are sure we would not have found by other means, or giving us enough understanding and confidence to make aggressive performance optimizations without sacrificing correctness." Stated gap, same paper: "While we would like to verify that the executable code correctly implements the high-level specification, or even generate the code from the specification, we are not aware of any such tools that can handle distributed systems as large and complex as those we are building." Also, one system "Improved confidence. Failed to find a liveness bug as we did not check liveness." This paper is pre-2022; I use it as the baseline the later papers respond to.

AWS practice, 2025 view. FACT, Brooker and Desai, "Systems Correctness Practices at AWS," ACM Queue, Feb 2025, https://queue.acm.org/detail.cfm?id=3712057: "AWS has adopted model checking, fuzzing, property-based testing, fault-injection testing, deterministic simulation, event-based simulation, and runtime validation of execution traces. Formal methods have been an important part of the development process - perhaps most importantly, formal specifications as test oracles that provide the correct answers for many of AWS's testing practices." INFERENCE: AWS's own summary leans on specs as test oracles, not on proofs of distributed implementations.

P language and PObserve. FACT, same article: "In 2023, the P team at AWS built PObserve, which provides a new tool for validating the correctness of distributed systems both during testing and in production. With PObserve, we take structured logs from the execution of distributed systems and validate post-hoc that they match behaviors allowed by the formal P specification of the system. This allows for bridging the gap between the P specification of the system design and the production implementation (typically in languages like Rust or Java)." So the design-to-code gap is handled by checking logs, not proof. Open problem named in the same article: "metastable failures remind us that systems have a variety of behaviors that cannot be neatly categorized this way [safety or liveness]." AWS answers that with simulation, not verification.

ShardStore (S3 storage node), 2021. FACT, Bornholt et al., SOSP 2021, https://dl.acm.org/doi/pdf/10.1145/3477132.3483540 (local PDF). What was checked: "functional correctness of API-level calls, crash consistency of on-disk data structures, and concurrent correctness of API calls and background maintenance tasks", on "over 40,000 lines of Rust". Method and stated weakness: "we were willing to accept weaker correctness guarantees than full formal verification, which is currently impractical for storage systems at this scale and level of complexity." Limits: "our validation checks can miss bugs[,] their reporting success does not mean the code is correct, only that they could not find a bug." Also: "Our validation approach thus far deals only with sequential correctness" for the conformance check (concurrency is checked separately with stateless model checking). Scope is one node: "replicates object data across multiple storage nodes, so single-node crash consistency issues do not cause data loss." The multi-node S3 system is outside this paper.

Zelkova (IAM policies), 2018. FACT, Backes et al., FMCAD 2018, https://discovery.ucl.ac.uk/id/eprint/10081411/1/Semantic-based%20Automated%20Reasoning%20for%20AWS%20Access%20Policies%20using%20SMT.pdf: "ZELKOVA solves a PSPACE-complete problem and is invoked many millions of times daily." And "this work is one of the largest and most widespread uses of formal methods in industry." Gap: "If ZELKOVA is unable to handle any construct in the policy or the solver times out, it returns unknown." Future work they list: concrete request contexts as counterexamples and policy repair. INFERENCE: it checks policies against a formal model of the policy language; I did not see a claim that the IAM enforcement code itself is verified.

Cedar (authorization), 2024. FACT, Cutler et al., OOPSLA 2024, https://arxiv.org/abs/2403.04651: "We have modeled Cedar in the Lean programming language, and used Lean's proof assistant to prove important properties of Cedar's design. We have implemented Cedar in Rust." Proved: "Forbid trumps permit"; "Default deny"; "Explicit allow". The Rust code is not proved; it is tested against the Lean model: "we use extensive differential random testing [...] to confirm that our Rust code and Lean model agree." Companion paper, "How We Built Cedar" (Disselkoen et al., AWS, 2024, local): "While carrying out proofs, we found and fixed 4 bugs in Cedar's policy validator, and DRT and PBT helped us find and fix 21 additional bugs". Stated gap: "Cedar's testing framework has missed bugs, too. The most notable example is that it did not discover the non-termination bug". On proving Rust directly: "tools for verifying Rust code are not (yet) up to the task, e.g., they cannot handle much of the standard library, they support only certain code idioms, they sometimes have trouble scaling". Note a source conflict: Brooker and Desai 2025 say Cedar "implementation was built in the verification-aware programming language Dafny"; the OOPSLA and HWBC papers say Lean. I do not know why; possibly an earlier Dafny model. Not checked further.

s2n (TLS), 2018. FACT, Chudnov et al., CAV 2018, https://link.springer.com/content/pdf/10.1007/978-3-319-96142-2_26.pdf: proofs are re-run at each code change ("proofs are automatically re-established with little to no interaction from the developers"). Gaps, same paper: "Since SAW does not support induction, we prove that this statement holds for a finite number of key and message sizes." "The result is that our proof assumes correct implementation of the hash functions." "The library implements only a subset of the standards, thus we can only prove a simulation relation and not equivalence." "In future work we plan to expand the scope of our proof to allow us to formally establish full corking safety."

Kani and the Rust standard library, 2026. FACT, Delmas et al., arXiv 2607.01504 (local): Kani "pushes bounded model checking beyond bug-finding"; AWS used it on the Firecracker block-device boundary (Brooker and Desai 2025: "prove key properties of this security boundary"). FACT, Cook et al., "Verifying the Rust Standard Library," NFM 2026, arXiv 2606.17374 (local): the "largest verification campaign reported for a software library"; remaining obstacles "(e.g., generic function verification, intrinsic modeling, and concurrency)" are framed "as open problems for the formal-methods community". INFERENCE: Kani covers memory-safety-style properties of single-process Rust; multi-node and concurrent protocol properties are not what it proves.

Critical evaluation, 2026. FACT, Woodcock and Larsen, Formal Aspects of Computing 2026, https://dl.acm.org/doi/pdf/10.1145/3815784: "the evidence base is selective and does not support organisation-wide claims about prevalence, cost-effectiveness, or ROI; quantitative baselines are sparse, and survivorship bias is plausible." Challenge named: "maintaining specifications under continuous evolution". OPINION: take AWS success claims as case reports, not measured effect sizes.

### Azure / Microsoft

CCF (Azure Confidential Ledger), 2025. FACT, Howard et al., NSDI 2025, https://www.usenix.org/system/files/nsdi25-howard.pdf: "smart casual verification [...] combines the rigor of formal specification and model checking with the pragmatism of automated testing, in our case binding the formal specification in TLA+ to the C++ implementation." Result: "find six subtle bugs in the design and implementation before they could impact production." Why it was needed: "CCF's consensus logic, though based on Raft [74] has been sufficiently modified such that it is now based on an unproven algorithm." Gaps in their words: "We found exhaustive model checking too time-consuming to run with all but the strongest state constraints in our CI pipeline"; "This led us to limit the state space more than we would have liked. We could have used a proof system, such as the TLA+ Proof System, instead of a model checker." And on the implementation link: "Prior to our trace validation efforts [...] we were not confident that our consensus spec matched the implementation." INFERENCE: the guarantee is "bounded model checking of the spec plus trace validation of test executions", not a proof about the C++.

Cosmos DB, 2023. FACT, Hackett, Rowe, Kuppe, ICSE-SEIP 2023, https://arxiv.org/abs/2210.13661: they verified "10 liveness properties and 14 safety properties across the 4 distinct data consistency levels", by "exhaustive state space exploration of logs up to length 6, and depth-first random simulation of execution traces exploring up to 100 steps." The spec describes user-visible behavior only. Stated gap: "Our lack of interaction with Cosmos DB's implementation is a double-edged sword, in that it is possible that some error in our specification has escaped the notice of those reviewing it." On trace validation: "impractical due to the size and complexity of Cosmos DB's implementation. While this is a fundamental limitation of our approach [...]". Payoff: the spec was used to "offer a fundamental solution to a previous high-impact outage within another Azure service that depends on Cosmos DB."

Coyote (formerly P#), 2016. FACT, Deligiannis et al., FAST 2016, https://www.usenix.org/system/files/conference/fast16/fast16-papers-deligiannis.pdf: "Formal techniques, such as TLA+, can only verify high-level specifications of systems at the level of logic-based models, and fall short of checking the actual executable code." Their answer is systematic testing of the real code, applied to Azure Storage vNext and others; it found "a subtle liveness bug that only intermittently manifested during stress testing for months". This is testing, not verification. Later Coyote papers (Scholar snippets only, not read in full): Deligiannis et al., "Building reliable cloud services using Coyote actors," SoCC 2021; Deligiannis et al., TACAS 2023.

Network verification at Azure. Scholar snippet only (Jayaraman et al., "Validating datacenters at scale," SIGCOMM 2019, https://dl.acm.org/doi/pdf/10.1145/3341302.3342094): "using formal methods and automated theorem proving for network operation at scale. [...] Our experience with deploying network verification in Azure suggests that there is another [...]". I did not read the paper, so I record no gaps for it.

### Meta

FACT, Carbonneaux et al., "Applying Formal Verification to Microkernel IPC at Meta," CPP 2022, https://dl.acm.org/doi/abs/10.1145/3497775.3503681 (local PDF): "Static program analysis has been developed and used extensively at Meta, but not formal program verification of full functional correctness." They verified two queue data structures in Coq/Iris; "The proof work was completed in person months, not years". Limits, their words: "We assume a sequentially consistent memory model rather than the actual weak memory model of C." "Our specifications do not make any claims about liveness." This is an OS component, not a distributed system. I found nothing from Meta on verifying distributed or web services.

### Google

I don't know. Scholar query 13 returned academic papers (AutoMan, TLA+ proof system, Multi-Paxos verification) and no Google verification paper. Not searched further because of the CAPTCHA.

### Network configuration (Batfish)

FACT, Brown et al., "Lessons from the evolution of the Batfish configuration analysis tool," SIGCOMM 2023, https://dl.acm.org/doi/pdf/10.1145/3603269.3604866: "It has evolved from a research prototype to an industrial-strength product, guided by scalability, fidelity, and usability challenges encountered when analyzing complex, real-world networks." Gap: "analysis fidelity issues arose mostly from undocumented semantics of router software." "The level of protection against modeling gaps this framework provides depends on the likelihood of encountering an untested deviation." They also say the real obstacle is deployment: "the diversity of frameworks makes it challenging to develop and deploy verification tools." INFERENCE: this is analysis of a model of vendor behavior, so it is only as good as that model; it is verification of configs, not of router software.

## 3. Academic

IronFleet, 2015 (baseline, pre-2022). FACT, Hawblitzel et al., SOSP 2015, doi 10.1145/2815400.2815428 (local PDF): "Regarding liveness, IronFleet breaks new ground: to our knowledge, IronFleet is the first system to mechanically verify liveness properties of a practical protocol, let alone an implementation.". Trusted base: "the spec for each system is trusted, as is the brief main-event loop"; "We assume the correctness of Dafny, the .NET compiler and runtime, and the underlying Windows OS." Network assumption: "We do assume the network does not tamper with packets".

Verdi, 2015 (baseline). FACT, Wilcox et al., PLDI 2015 (local PDF): "This paper focuses on safety properties for distributed systems; we leave proofs of liveness properties for future work."

What breaks in verified systems. FACT, Fonseca et al., EuroSys 2017, doi 10.1145/3064176.3064183 (local PDF): "we found a total of 16 bugs" in IronFleet, Verdi and Chapar, "caused by violations of a wide-range of assumptions on which the verified components relied. [...] these assumptions referred to a small fraction of the trusted computing base, mostly at the interface of verified and unverified components." Pre-2022, but still the best evidence that the gap is at the boundary.

Verus (2024) and IronKV port. FACT, Lattuada et al., SOSP 2024, doi 10.1145/3694715.3695952 (local PDF): "We skip the protocol level, since Dafny and Verus share similar mathematical modeling tools and are likely to admit very similar proofs." The port's README (local, verus-lang verified-ironkv) says: "this repository only verifies the 'host program' from IronFleet. IronFleet also proves that the host program TLA state machine model, in the context of a distributed system, implements the high-level spec. This repository doesn't replicate that layer of proof." INFERENCE: the Verus port covers per-host implementation, not the distributed-level refinement or liveness.

Grove, 2023. FACT, Sharma et al., SOSP 2023 (local PDF): verified "vKV, a realistic distributed multi-threaded key-value store", with "supports reconfiguration, primary/backup replication, and crash recovery"; "67-73% of Redis on a single core". Gap: "One limitation is that Grove is only able to verify safety properties, ensuring that a system never returns the wrong results. Grove cannot verify liveness properties". Cost: "verification required 12x the lines of proof as lines of code". Perennial (SOSP 2019, local) is Grove's crash-safety base; I did not extract its limits here.

Anvil, 2024. FACT, Sun et al., OSDI 2024, https://www.usenix.org/conference/osdi24/presentation/sun-xudong (local PDF): verified liveness of three Kubernetes controllers (ZooKeeper, RabbitMQ, FluentBit) in Rust/Verus, "with the proof-to-code ratio ranging from 4.5 to 7.4". Assumptions, their words: "(2) The controller environment model correctly describes the interactions between the controller and its environment. (3) The specification of the unverified APIs for querying and updating the cluster state correctly describes the behavior of these APIs. (4) The verifier (Verus and Z3), the Rust compiler, and the underlying operating system are correct." Fault model: "an arbitrary number of faults can happen, but eventually faults stop happening." And other controllers must be assumed to stop interfering ("Anvil assumes that the StatefulSet controller eventually stops updating the stateful set until the target controller updates the stateful set again"). INFERENCE: the Kubernetes API server and other controllers are specified, not verified; this is the closest the field has to verified liveness of a deployed-style cloud component, and it covers one controller at a time.

Basilisk, 2025. FACT, Zhang et al., OSDI 2025, https://www.usenix.org/conference/osdi25/presentation/zhang-tony (local PDF): "apply it to 16 distributed protocols, including complex ones like Multi-Paxos. Basilisk automatically finds inductive invariants". The target is "to prove that a protocol satisfies a desired safety property". INFERENCE: protocol-level safety only; no code and no liveness in the abstract.

Veil, 2025-26. Scholar snippet (Pirlea et al., CAV 2025, not read): "Veil can verify a variety of distributed protocol specifications without the [...]". Local: Pirlea et al., "Lessons from Building an Auto-Active Verifier in Lean," Dafny Workshop 2026, argue the verifier is built inside Lean. I did not extract protocol-scale limits.

AutoMan, 2025. FACT, Zhang et al., SOSP 2025 (local PDF): generates implementations and proof obligations "without placing trust in the code generator" and reduced effort "70%-97% for Multi-Paxos". Limit: "Another limitation of AutoMan is that it currently does not support generating multi-threaded programs."

TraceLink, 2025. FACT, Hackett and Beschastnikh, OOPSLA 2025, https://doi.org/10.1145/3763128 (local PDF): "these code extraction and compilation tools are themselves unverified. So, even though the design is checked, the output implementation may deviate from the design". They found "9 previously undetected and diverse bugs in PGo's TCB".

VeriSMo, 2024. FACT, Zhou et al., OSDI 2024, https://www.usenix.org/conference/osdi24/presentation/zhou (local PDF): "fully verified for functional correctness, secure information flow, and VM confidentiality and integrity." It is a single-machine security module, not a distributed system. Out of scope: "Denial-of-service attacks are possible"; "Physical attacks are out of scope". Trusted: "VERISMO fully trusts a small number of primitive functions, ground-truth axioms, the hardware model specification [...]". Hawblitzel and Lorch are authors on both VeriSMo and Verus. Relevance here: shows Verus works for security-critical industrial code, one machine at a time.

Atmosphere, 2025. FACT, Chen et al., SOSP 2025, doi 10.1145/3731569.3764821 (local PDF): "6K lines of executable code required an effort of less than 2.5 person-years"; "proof-to-code ratio of 3.32:1". Limits: "we only reason about the effects of system calls, but not the user code"; timing channels remain. A microkernel, not distributed.

Survey (low confidence). FACT, Bondarev et al., "SoK: Formal Verification of Consensus Protocols," arXiv 2608.21935, Aug 2026 (local): "liveness verification remains underdeveloped despite its importance for progress guarantees; specification-implementation disconnects undermine real-world assurance; and scalability limits restrict verification to small networks." Caveat: single arXiv preprint, blockchain-focused, not peer reviewed in my sources; I use it only as a second voice, not as evidence.

## 4. Cross-cutting gaps (INFERENCE from the quotes above)

1. Design to implementation. AWS (Newcombe 2014: "not aware of any such tools"), CCF ("unproven algorithm", trace validation), Cosmos (trace validation "impractical"), TraceLink (compiler "unverified"), PObserve (logs vs P spec). Every industrial answer is testing or log checking. The only proved distributed implementations (IronFleet, Verdi, Grove, Anvil) are research systems.

2. Liveness. Verdi and Grove: safety only. IronFleet and Anvil: liveness, under explicit fairness and fault assumptions. Meta: "no claims about liveness". Brooker 2025 says metastable failures fit neither safety nor liveness.

3. Concurrency plus failures in real code. ShardStore: sequential conformance plus separate model checking; Grove: safety only; Rust std: concurrency is an open obstacle.

4. The trusted spec and the model of the environment. IronFleet: spec trusted. Anvil: environment model and API specs assumed. Batfish: undocumented vendor semantics. Cosmos: possible spec error "escaped the notice of those reviewing it". Fonseca: bugs sit at the verified/unverified boundary.

5. Spec maintenance and evidence. Woodcock and Larsen: "maintaining specifications under continuous evolution"; CCF solves this with CI; most others do not say.

6. Cost. Proof-to-code ratios in my sources: 3.32 (Atmosphere), 4.5-7.4 (Anvil), about 12 (Grove).

## 5. Candidate big problems (OPINION, ranked by how directly my sources support them)

A. Conformance between an industrial distributed implementation and its verified or model-checked design, strong enough to turn "found 6 bugs" into a guarantee. Support: items 1 and 4. Open question I cannot answer from sources: how much of CCF-style trace validation can be upgraded to proof for the traced behaviors.

B. Liveness and fault-tolerance of real multi-component cloud control planes (Anvil-style, but across several controllers and the API server rather than one). Support: item 2; Anvil's own assumption about other controllers.

C. Concurrent, crash-prone single-node storage engines at ShardStore scale, with proofs instead of testing. Support: ShardStore "currently impractical"; item 3. Risk: heavy proof cost (12x ratio at Grove).

D. Specification quality: how to know the trusted spec and environment model are right. Support: item 4. This is the verification-side problem least addressed by any tool in my sources.

I do not know which of these has the largest impact; that is the advisor's criterion and needs evidence on incident causes that I did not collect.
