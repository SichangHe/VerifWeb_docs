# vlm43_vector: a validated hot reload that stops Vector

(authored by agents)

Why: vlm42 asked whether open-source Rust has a Cloudflare-style case, where a config the validator accepts is pushed at runtime and crashes the consumer. Motivation, quoted in out/vlm42_config/postmortems.md, from Cloudflare 18 Nov 2025: "When the bad file with more than 200 features was propagated to our servers, this limit was hit — resulting in the system panicking."

Takeaway (FACT, from reading source plus my own repro and Verus). Yes. In Vector (commit 515e87d, 2026-11-10), setting `scrape_interval_secs: 0` on an `internal_metrics` source passes both `vector validate` and the reload's build step. The source task then panics, and Vector shuts the whole process down. A hot reload (SIGHUP or file watch) is enough to trigger it. "Validator accepts x implies no panic" is false for this field. It becomes true once the validator rejects 0, and the Verus proof covers exactly that.

Mechanism (FACT, source). src/sources/internal_metrics/mod.rs:121 only warns: "Interval set to 0 secs, this could result in high CPU utilization. It is suggested to use interval >= 1 secs." Then `build` returns Ok. Line 194 calls `time::interval(self.interval)`, and tokio asserts "`period` must be non-zero." `vector validate` (src/validate.rs:384, 420) runs `build` and the healthchecks, but never runs the tasks. A reload works the same way: `reload_config_and_respawn` (src/topology/running.rs:313) builds the new pieces, runs the healthchecks, and spawns them. The spawned source is wrapped in `handle_errors` (running.rs:1413, mod.rs:61). That wrapper catches the panic and sends an abort, and app.rs:376 turns the abort into `SignalTo::Shutdown`. So the panic is contained, but it still takes down the whole process. A careful operator who runs `vector validate` before pushing gets a green result.
Same pattern (FACT from reading only, not reproduced): `static_metrics` `interval_secs` (warns on 0, same code shape); `host_metrics` `scrape_interval_secs` (no check at all, mod.rs:343); `http_client` `scrape_interval_secs` (only warns when timeout > interval, util/http_client.rs:207). By contrast, `throttle` and `aggregate` already reject 0. INFERENCE: someone fixed this per component, not by rule.
Fractional values: 1e-10 s rounds to a zero Duration and also panics (repro, third case).

Evidence.
- repro/ (my own Cargo project; it uses only tokio 1.49.0, Vector's version, plus serde_with, and does not depend on Vector, because Vector is not a published crate). It copies the deserialize, warn-only build and interval steps, and the catch_unwind. The output is "{"scrape_interval_secs":0}: build Ok, run PANIC: Some("`period` must be non-zero.")". Interval 1 runs fine. Limit: this does not run Vector itself. I did not run any Vector binary, per the rules.
- verus/vector_interval.rs: "7 verified, 0 errors". It proves the claim false (witness 0), and that `reload` is panic-free with a validator that rejects 0. Negative check: swapping in the real warn-only validator fails with "precondition not satisfied". The model is small: Duration is u128 nanoseconds, and tokio's assert is a precondition.

Other reload-path findings (INFERENCE, not confirmed). running.rs has many `unwrap()` calls that rely on internal bookkeeping invariants, for example `previous.await.unwrap().unwrap()` at line 776 on old sink tasks. If an old sink had already failed, this would panic during reload. But a sink failure already aborts Vector, so I see only a race, and no config-only trigger. Rollback (running.rs:372-401) can end in "Failed to restore old configuration." after old components were already shut down. That can wedge Vector into a partial topology, but it needs the old config to stop building (for example an env or file change), so it is not driven by config alone. Neither was proved.

Assessment (OPINION). This is the first case found that is a runtime push, not just startup, which answers vlm42's open question. Severity is low: it is local operator config, not a fleet-wide feed, and the shutdown is graceful. It is a clean, cheap, mechanizable instance of a validator/consumer gap: the consumer's precondition (tokio's assert) is invisible to the validator. It supports the "derive the validator from the consumer's obligations" idea. Not published or filed anywhere. No new literature search was done (see vlm42 prior_work.md).
