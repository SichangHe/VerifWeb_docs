# Independent review of candidate verification targets
(authored by agents unless marked 🧑)

Reviewed `out/vlm_targets/TARGETS.md` against freshly fetched primary pages/PDFs, the meeting transcript, and two small independent checks. Original reports and code were not modified. This file distinguishes confirmed historical reports from reproduced vulnerabilities: I did not rebuild historical browser releases. Source captures are in `target_sources/`; independent runnable checks are in `target_repros/check.js` and `check.log`.

## Actionable findings

1. **Wrong: the specifications are not already executable.** TARGETS.md:18 says “each with an executable spec”; :139 says “WHATWG/ECMA are executable specs.” These standards contain algorithms expressed as prose/pseudocode; no executable reference or translation is named. Indeed :86 proposes “a hand-transcribed spec.” Call them algorithmic standards; identify the executable oracle separately and state the trust placed in the transcription. The URL standard itself specifies an idempotence goal: “a non-failure result of a parse-then-serialize operation will not change with any further parse-then-serialize operations applied to it.” [WHATWG URL](https://url.spec.whatwg.org/#goals). This does not make the document executable or establish feasibility of verifying the full parser.

2. **Overstated: novelty from absence of a search hit.** :85 says “This would be the first.” Its actual cited survey says “I didn't find any source showing that Servo components have been formally verified with Kani, Verus or Creusot.” That supports only a search result, not priority. Likewise :49, “most verified-compiler work proves passes one at a time,” supplies no corpus or evidence, and compositional pass proofs can preserve cross-pass invariants. Replace both with bounded, explicitly unchecked gap statements. “Most bite-sized” and “highest-impact” are judgments, not independently established results.

3. **Wrong as a quotation: an agent paraphrase was promoted into source words.** :45 quotes “after write-barrier elision was already decided.” This is the `Class:` paraphrase in src_engine.md, not the Project Zero quotation. Project Zero instead writes: “A check before EarlyOptimizationPhase in SimplifiedLoweringPhase makes the correct assumption that write barriers can be elided when storing anything to a field in an object with the TaggedSigned representation.” [CVE-2021-4102 RCA](https://googleprojectzero.github.io/0days-in-the-wild/0day-RCAs/2021/CVE-2021-4102.html). The mechanism is confirmed; remove the false quotation marks.

4. **Overstated: fuzzing is not categorically blind.** :33 says “That's runtime verification where fuzzing is blind.” Project Zero qualifies the difficulty: “without specific compiler instrumentation” these bugs “don’t normally result in observable misbehaviour at runtime (i.e., a crash).” [CVE-2020-6418 RCA](https://googleprojectzero.github.io/0days-in-the-wild/0day-RCAs/2020/CVE-2020-6418.html). The proposed monitor is precisely extra instrumentation for a fuzzer; the quote does not establish a novel distinction. The second cited bug was detected by Fuzzilli: “This is how Fuzzilli triggered the bug.” [CVE-2019-11707 RCA](https://googleprojectzero.github.io/0days-in-the-wild/0day-RCAs/2019/CVE-2019-11707.html).

5. **Overstated/underspecified: memory isolation and object reachability are different contracts.** :62 requires every attacker-influenced access to land inside the cage, while :65 proposes an *external*-pointer table. V8 explicitly seeks to “prevent memory corruption outside of the sandbox,” not to forbid every legitimate mediated access outside it. [V8 Sandbox](https://v8.dev/blog/sandbox). Specify allowed external accesses, guard-page traps, and the threat model. For target 6, a present heap graph cannot establish absence of future leaks, native-pointer access, or speculative leaks. NodeProf is “Instrumentation framework for Node.js compliant to ECMAScript 2020 based on GraalVM”; it is not a V8 heap monitor. [NodeProf](https://github.com/Haiyang-Sun/nodeprof.js). The proposed two-context experiment is useful, but the promise that it detects vm2's escape remains unverified. Spook.js is deliberately outside the target's stated Spectre scope; label it contextual motivation, not a failure caught by this property.

6. **Wrong if read as an equivalence: event-loop conformance does not imply race freedom.** :98 combines draining microtasks with “A script's outcome doesn't depend on the order of unordered events (race-freedom).” The HTML rule says “While the event loop's microtask queue is not empty” and “Run oldestMicrotask”; it does not constrain every pair of independent future tasks. [HTML microtask checkpoint](https://html.spec.whatwg.org/multipage/webappapis.html#perform-a-microtask-checkpoint). Two independent callbacks that set the same variable to different values produce different results in different permitted orders, despite an empty microtask queue throughout; `target_repros/check.log` records `B` versus `A`. Split these into separate engine-conformance and application-determinism properties. Determinism and absence of conflicting unordered accesses also are not interchangeable definitions.

7. **Overstated: the cited numeric example does not establish a defective typer rule.** :37 properly admits partial uncertainty, but target 2 uses CVE-2021-21220 as support for a range-transfer bug. ZDI says “In the event that JITted code produces an erroneous numeric result” the exploit can fool range-based optimization. [ZDI](https://www.thezdi.com/blog/2021/12/15/exploitation-of-cve-2021-21220-from-incorrect-jit-behavior-to-rce). A correct abstract transfer function can disagree with incorrectly compiled concrete execution. Preserve the caveat and use an independently established transfer-function bug to justify this particular target.

8. **Overstated: broad policy and monitoring examples need explicit limits.** :90 gives a sanitizer-tree fixed point without naming the sanitizer, parsing context, namespace, or meaning of “script-capable.” HTML parsing alone is not sanitization. :112 snapshots only `Object.prototype`, whereas :110 quantifies over all built-in prototypes; before/after snapshots also miss transient mutation. An independent check temporarily adds and removes a prototype field: the intermediate read returns `123`, but the before/after comparison reports no change. :122 logs input reads and destinations; this does not establish a flow of sensitive bytes between them, including encoded or implicit flows. Present these as exploratory checks, not implementations of the full properties.

## Claim ledger

Classifications below cover the remaining assertions, including proposals whose feasibility cannot yet be verified.

- **Meeting request and framing — confirmed.** The transcript says “Don't jump at one idea. Write down 10 different things that you might like to verify, either about individual JavaScripts or the engine itself.” It also says “And the runtime verification has the dynamic state context, and that's the difference. The question is, for the given state, what is the behavior of this? As opposed to, for any given state, what is the behavior?” Source: `/ssd1/sichangheagent/email/1103madhyastha_govindan_ghavidel.vtt`, lines 503 and 506. The second action at 555–556 is present. The “possibly novel” remark is at 500, not 503. The tab-isolation discussion at 474–481 is present. Crawling infrastructure at :121 is **overstated by its citation**: 439–447 says “we have lots of data, we have lots of experience,” not that a crawler is ready for checkout instrumentation.
- **Four-layer grouping — confirmed as the author's organization**, not a taxonomy established by the sources. “Each target lists ... a differentiator” (:25) is **wrong literally**: targets 4, 8–11 and 13 have no differentiator entry.
- **V8 statistic — confirmed.** Project Zero: “Chromium had a record high number of 0-days detected and disclosed in 2021 with 14”; list entry: “6 JavaScript Engine - v8”. [2021 review](https://projectzero.google/2022/04/the-more-you-know-more-you-know-you.html). It includes GC vulnerabilities, so it does not itself rank JIT targets above all others.
- **Isolation cost — confirmed with scope.** Reis et al.: “it incurs a total memory overhead of 9-13% in practice”; this evaluates deployed desktop Chrome Site Isolation, not arbitrary process-per-tab configurations. [USENIX PDF](https://www.usenix.org/system/files/sec19-reis.pdf). Cloudflare: “When using strict process isolation in Workers, we find the CPU cost can easily be 10x what it is with a shared process.” [Workers security model](https://blog.cloudflare.com/mitigating-spectre-and-other-security-threats-the-cloudflare-workers-security-model/). These are distinct workloads, resources, and baselines.
- **Target 1 historical failures — confirmed.** PZ: “kJSCreate can have side-effects, for example by using a Proxy as third argument to Reflect.construct.” [2020 RCA](https://googleprojectzero.github.io/0days-in-the-wild/0day-RCAs/2020/CVE-2020-6418.html). PZ: “the JIT failed to ensure that calling Array.prototype.pop would not end up loading an array element from a prototype of the array.” [2019 RCA](https://googleprojectzero.github.io/0days-in-the-wild/0day-RCAs/2019/CVE-2019-11707.html). Invalidating all facts for every heap write is a conservative proposal, stronger than necessary when writes cannot affect the relevant object. The exact function, current opcode coverage, ~200-line estimate, Turbolizer workflow, and monitor feasibility are **unverifiable here**; no implementation is supplied in this document.
- **Target 2 VeRA — confirmed.** Brown et al.: “We use VeRA to translate and verify Firefox range analysis routines”; the PDF's reference format identifies PLDI ’20. [Paper](https://www.cs.utexas.edu/~hovav/dist/vera.pdf). The soundness property is a coherent proposal. Universal absence of verified V8/Maglev typers and success of an LLM translation are **unverifiable**; the text appropriately labels them unchecked/proposed.
- **Target 3 second failure — confirmed.** PZ: “without generalizing the FieldType, and so without deoptimizing any code that still relies on the previous FieldType.” [CVE-2022-3723](https://googleprojectzero.github.io/0days-in-the-wild/0day-RCAs/2022/CVE-2022-3723.html). This is dependency invalidation, not demonstrated here to be a phase-ordering bug. A heap verifier is not by itself a proof/check of all IR invariants; proposed coverage is **unverifiable**.
- **Target 4 — confirmed historical failure; proposed proof unverified.** PZ: “live objects may remain unmarked and be collected, leading to use-after-free.” [CVE-2021-37975](https://googleprojectzero.github.io/0days-in-the-wild/0day-RCAs/2021/CVE-2021-37975.html). Specify ephemeron-table liveness as well as key liveness. Iris/CakeML prior-GC references lack identifiable works here and are **unverifiable in this review**.
- **Target 5 — confirmed historical failure and threat-model quotation.** Wasmtime: “a 35-bit effective address instead of WebAssembly's defined 33-bit effective address.” [Advisory](https://github.com/bytecodealliance/wasmtime/security/advisories/GHSA-ff4p-7xrq-q5r8). V8: “it is assumed that an attacker can read and write arbitrarily inside the V8 Sandbox.” [Sandbox](https://v8.dev/blog/sandbox). VeriWasm exists and validates native isolation: “All linear memory accesses must fall within the linear memory bounds (or surrounding guard pages).” [Paper](https://cseweb.ucsd.edu/~dstefan/pubs/johnson:2021:veriwasm.pdf). Crocus/VeriISLE details and absence of pointer-table verification remain **unverifiable here**; delegated prior-work review should assess them independently.
- **Target 6 — confirmed historical quotation, not a current exploit reproduction.** Advisory: “vm2 was not properly handling host objects passed to Error.prepareStackTrace in case of unhandled async errors.” [vm2 advisory](https://github.com/advisories/GHSA-7jxr-cg7f-gpgv). Cloudflare: “Virtual machines have bugs, containers have bugs, and yes, isolates (which we use) also have bugs.” [Workers](https://blog.cloudflare.com/mitigating-spectre-and-other-security-threats-the-cloudflare-workers-security-model/). Spook.js exists ([site](https://www.spookjs.com/)); the URL guessed for its PDF in src_isolation.md returns 404. “Cheaper than proving the whole engine” is a plausible but unmeasured proposal, **unverifiable as a cost result**.
- **Target 7 failures — confirmed historical reports.** Tsai: “It's all about the inconsistency between URL parser and requester.” [Black Hat slides](https://www.blackhat.com/docs/us-17/thursday/us-17-Tsai-A-New-Era-Of-SSRF-Exploiting-URL-Parser-In-Trending-Programming-Languages.pdf). rust-url report: `last_slash_can_be_removed("/y/z/C:/")` “sees the last dir is a drive letter (/C:/)”. [#1130](https://github.com/servo/rust-url/issues/1130). Lightpanda reporter gives `new URL("://foo.bar/path?query#fragment")` and “a.protocol => ":"”; the issue was “closed this as completed in #1170 on Oct 23, 2025.” [#1111](https://github.com/lightpanda-io/browser/issues/1111). Thus present-tense “accepts” is **overstated** without a pinned vulnerable version. Node independently yields `abc://x/y/z/` for the drive-letter example and `TypeError` for the invalid scheme. Lightpanda's checked Cargo manifest explicitly lists `url = "2.5.8"` and `html5ever = "0.40.0"` (`out/cx_bugs/lightpanda/source/src/rust/html5ever/Cargo.toml`); shared Rust dependencies are confirmed. Complete Servo dependency purity, WPT coverage of the proposed contract, direct Verus compatibility, and ESMeta extraction feasibility remain **unverifiable here**.
- **Target 8 advisories — confirmed.** “DOMpurify was vulnerable to nesting-based mXSS.” [CVE-2024-47875](https://github.com/advisories/GHSA-gx9m-whjm-85jf). “malicious HTML using special nesting techniques can bypass the depth checking.” [CVE-2024-45801](https://github.com/advisories/GHSA-mmhx-hmjr-r674). A bounded Kani harness against html5ever is a proposed experiment, **unverifiable** without a working harness and sanitizer/security predicate.
- **Target 9 failure — confirmed report.** Issue title is “Tasks executed in incorrect order”; its body says “The following code executes microtasks (promises are also microtasks) and then macrotasks (timeouts) on Chrome, Firefox and Safari.” [Lightpanda #1180](https://github.com/lightpanda-io/browser/issues/1180). Current Servo scheduling and EventRacer capabilities are not established by that report. The Petrov citation's linked DOI in src_programs.md is not independently verified here; do not treat the recalled author list as confirmed.
- **Target 10 — confirmed reported GC bugs and historical unsafe-boundary quote.** Servo maintainer: “There are absolutely no guarantees that pointers are valid any more, since the JS objects could have been finalized and destroyed the corresponding Rust object.” [#24621](https://github.com/servo/servo/issues/24621). “if there's a native Rc<Promise> alive then its destructor will run and cause problems.” [#15318](https://github.com/servo/servo/issues/15318). The 2015 paper says wrappers/plugins “are still a source of bugs and one of our largest areas of unsafe code,” covering custom allocators and SpiderMonkey interoperation. [PDF](https://arxiv.org/pdf/1505.07383). The Drop prohibition is a conservative proposed rule; complete `JSTraceable` coverage and Miri/Kani execution through SpiderMonkey FFI are **unverifiable** here. A trace trait alone does not specify destructor behavior.
- **Target 11 — confirmed advisory and tool existence.** NVD: “The function defaultsDeep could be tricked into adding or modifying properties of Object.prototype using a constructor payload.” [CVE-2019-10744](https://nvd.nist.gov/vuln/detail/CVE-2019-10744). Jalangi calls itself “Dynamic analysis framework for JavaScript.” [Repository](https://github.com/Samsung/jalangi2). No chosen corpus or monitor exists in TARGETS.md; top-100 coverage is **unverifiable**. The policy may deliberately reject legitimate prototype-modifying utilities; define the intended library class.
- **Target 12 — partly confirmed.** Sansec: “However, in February this year, a Chinese company bought the domain and the Github account”; “this domain was caught injecting malware on mobile devices.” [Report](https://sansec.io/research/polyfill-supply-chain-attack). event-stream's issue confirms the injected dependency incident: “the injection is added to flatmap-stream”. [Issue](https://github.com/dominictarr/event-stream/issues/116). These do not establish payment-field exfiltration in every case. British Airways quote is **unverifiable in this round**: the cited archive returned HTTP 429. “Never ... off-origin” in the title is stronger than the proposed allowlist, which can authorize cross-origin payment processors. JSFlow/FlowFox details, crawler instrumentation, and pinned-hash coverage are **unverifiable here**.
- **Target 13 — confirmed outage and experimental engine; planned classification unverified.** Cloudflare: “contained a regular expression that backtracked enormously and exhausted CPU used for HTTP/HTTPS serving.” [Postmortem](https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/). V8: its experimental engine “guarantees execution in linear time with respect to the size of the subject string.” [V8 article](https://v8.dev/blog/non-backtracking-regexp). Target correctly distinguishes the Cloudflare example from JS. Fix the engine/version/flags, regex size assumptions, and dynamic-pattern policy before claiming linearity of npm patterns.
- **Closing questions/tool inventory — partly confirmed, partly overstated.** The listed classes of tools are reasonable proposals; this file offers no evidence that each applies to every listed substrate. “A proof covers every state” (:141) is **overstated**: it covers states satisfying its preconditions under its modeled semantics and trusted assumptions. Runtime checking need not run on production code. The C++/Rust distinction at :140 is **overstated**: Verus proofs of Rust reimplementations still need correspondence to production Rust, just as C++ models do. “Verus gives no counterexamples” is **unverifiable independently here**; the sibling report narrows it to the normal CLI path, which is the wording this document should use. The claim that all engine invariants are “undocumented” is **overstated**, especially when the cited RCAs document several. Existence/content of the further-candidate documents and the author's past failed searches are not proof claims; the search-history assertions are **unverifiable as historical statements**. No independently verified JSC/UXSS/sandbox-bypass case is supplied by TARGETS.md itself.
