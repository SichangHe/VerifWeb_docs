# Independent review of the Boa event-loop reports
(authored by agents unless marked 🧑)

Reviewed `out/cloud/p2_event_loop.md` (cloud) and `out/vlm3_boaloop/report.md` (vlm3), 2026-11-04. “Confirmed” below distinguishes rerun observations from source inspection; it does not certify historical execution records.

The timer/promise ordering defect is reproducible. The patch fixes all 4,171 failures in the supplied 9,430-program corpus. The formal checks succeed for their abstract models. However, the patch introduces a cancellation problem, and the headline “patched loop is verified” exceeds what was proved. The corpus bound also counts grammar nodes, not callbacks.

## Actionable findings

1. **High: preserve cancellation while draining promises.** The added `drain_promise_jobs` loops until empty without reading `self.stop`. A chain that continually enqueues another promise job never returns to the outer stop check. Previously, the snapshot finished and the outer loop checked cancellation on the next iteration. This is a source-level regression, even though starving timers with an infinite microtask chain matches HTML ordering. Boa's public contract says: “Setting the signal to `true` will exit the inner event loop and stop executing any pending jobs.” [Boa `get_cancellation_token`, pinned source](https://github.com/boa-dev/boa/blob/329e89748ed34e218fe593b4209b1dbe1d6eb64d/core/engine/src/job.rs#L901-L907). Check cancellation inside the drain and propagate cancellation so due timers are not dispatched afterward. A standalone reproducer is `cancel.rs`; execution status is recorded below.

2. **Medium: describe the formal result as verification of an abstraction.** Cloud §1 says “the patched loop is verified in Verus”; §7 correctly says “Nothing mechanically links them to `job.rs`, so the abstraction gap is unverified.” Only the latter is defensible for the implementation. `verus/event_loop.rs` omits cancellation, clock deadlines, intervals, generic/async/finalization jobs, exceptions, borrowing, and GC checkpoints. TLC has the same narrow scheduling scope. Neither result establishes that the Rust patch preserves the executor's public behavior. Keep the qualification beside the headline.

3. **Low: correct the bound and patch size.** Cloud §3a says “At most 4 callbacks”; its `C` production generates `P.then(cb).then(()=>log(x'))`, two callbacks. Four `C` nodes yield eight logged callbacks. The confirmed bound is ≤4 grammar nodes, depth ≤4, yielding 9,430 nonempty programs. Cloud §1's “36-line patch” means 36 additions plus 14 deletions, not 36 changed lines.

4. **Low: do not call the helper a complete HTML checkpoint.** Its comment says `HTML "perform a microtask checkpoint"`; it only drains promise jobs. The HTML algorithm additionally includes a reentrancy guard, rejected-promise notification and `ClearKeptObjects`. The patch retains `context.borrow_mut().clear_kept_objects()` once per outer iteration, rather than after each new drain. This does not invalidate the tested ordering property, but the comment and conformance language should name that narrower behavior. [HTML checkpoint](https://html.spec.whatwg.org/multipage/webappapis.html#perform-a-microtask-checkpoint): “If the event loop's performing a microtask checkpoint is true, then return”; “Perform ClearKeptObjects().”

## Claim-by-claim audit

### Core behavior, checker, and patch

- **Confirmed within the tested setup:** cloud “Boa's default event loop violates HTML ordering,” vlm3 “The claim holds,” and the four minimal counterexamples. Default `Context` plus registered timers behaves as reported. Calling it an HTML ordering mismatch is precise; claiming Boa promises full HTML event-loop conformance would be overstated.
- **Confirmed by source:** default-executor documentation, snapshot mechanism, and patch placement before timers, after each timeout/interval, and instead of the old promise snapshot. [Boa source](https://github.com/boa-dev/boa/blob/329e89748ed34e218fe593b4209b1dbe1d6eb64d/core/engine/src/job.rs#L863) says “A simple FIFO executor that bails on the first error” and “This is the default job executor for the [`Context`], but it is mostly pretty limited for a custom event loop.”
- **Confirmed:** the timer implementation cites HTML. [Timer module](https://github.com/boa-dev/boa/blob/329e89748ed34e218fe593b4209b1dbe1d6eb64d/core/wintertc/src/timers/mod.rs#L1-L7) says “TC55 timer APIs: `setTimeout`, `clearTimeout`, `setInterval`, `clearInterval`” and “Spec: <https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#timers>”. **Inference, not an established maintainer judgment:** vlm3's “spec-conformance bug relative to the spec Boa itself cites.” The evidence supports reporting the mismatch, not asserting maintainers' acceptance.
- **Confirmed:** all five grammar productions and FIFO Python model implement the described finite examples; one native fulfilled promise is shared; `C` schedules its second reaction after its first callback returns. `await_ticks=1/3` represents the cited native-fulfilled-promise cases. **Wrong wording:** the callback count described above. The corpus is not exhaustive over arbitrary JavaScript programs of four callbacks.
- **Confirmed for this grammar:** the `queueMicrotask` polyfill enqueues one promise reaction; these callbacks neither intentionally throw nor return thenables. **Overstated if generalized:** the polyfill is not a fully equivalent API, notably for exception reporting.
- **Confirmed:** fresh `Context` per harness input line; fresh process per Node/CLI program. **Unverifiable here:** Chromium's execution isolation and Playwright-specific setup/history, since Chromium was not rerun.
- **Confirmed by rerun:** original 4,171 and patched zero failures, current Node zero, total 9,430. **Unverifiable as historical facts:** eight identical 680-case runs, cloud failure-class count “148 of 212,” and all claimed run/load histories. Stored artifacts support reported counts but do not independently prove the runs occurred as described.
- **Overstated inference:** “No program without `setTimeout` fails, so promise-job FIFO itself is correct in Boa.” Finite passing traces support this grammar; they do not prove arbitrary promise-job behavior. Source queue operations additionally support FIFO in the modeled case.
- **Overstated absolute:** “a 0 ms timer is always already due at the next iteration.” Original source uses `split_off(&now)`, retaining keys equal to `now`. Expiration requires the clock to advance past the deadline; `Context` can use a fixed clock. The ordinary real-clock reruns reproduce the defect, so it does not depend on the absolute assertion.
- **Confirmed as a bounded result, not general correctness:** patch removes all tested mismatches. Generic jobs remain snapshot-based, and interval/nonzero-delay semantics are excluded by the report itself. Cancellation was omitted from both reports.
- **Unverifiable opinions:** “Severity is moderate,” “likely yes” about maintainer acceptance, and the proposed future architecture are recommendations, not demonstrated facts.

### Formal checks

- **Confirmed:** TLA+ state and nondeterministic spawning match their description: each step spawns at most two jobs within `Budget`, and all modeled timers are immediately eligible. `MicroFIFO` and `TaskFIFO` compare started prefixes against enqueue sequences; `NoTaskWithPendingMicrotasks` checks the sticky `bad` flag. This expresses the stated narrow ordering property.
- **Confirmed at Budget 8:** reported passing state counts and failing original/Node schedulers. **Unverifiable in this round:** all Budget-5 counts, since those configs were not rerun.
- **Confirmed:** the Verus oracle has `external_body`, `run_timer` requires an empty microtask queue, and the ghost sequence records microtask order. `exec_allows_no_decreases_clause` means this establishes partial correctness, not termination. No hidden `assume` or admitted scheduler obligation was needed in the inspected proof.
- **Confirmed with scope correction:** both reported Verus result counts reproduce with the older toolchain used by vlm3. **Unverifiable here:** exact cloud toolchain execution/version and the blanket claim about all constructs unsupported by Verus. A direct proof of Boa's implementation has not been supplied regardless of tool support.
- **Confirmed limitation:** cloud's “The model is validated against Chromium, not against the spec text” correctly disclaims a formal derivation. Agreement among engines is evidence, not proof. “Three checkers for the same property” is approximate: the trace checker additionally tests observable await/chained-reaction order; the formal models abstract these as generic spawned jobs.

### Specifications and historical sources

These quotes were checked against the primary pages/API, not taken on trust from the reports. HTML pages are live standards, not pinned historical editions.

- **Confirmed:** [HTML event-loop processing](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model) says “Perform oldestTask's steps” followed by setting the running task to null and “Perform a microtask checkpoint.” [Checkpoint](https://html.spec.whatwg.org/multipage/webappapis.html#perform-a-microtask-checkpoint) says “While the event loop's microtask queue is not empty” and “Let oldestMicrotask be the result of dequeuing from the event loop's microtask queue.” The report's slashes and numeric outline are edited formatting, not a literal continuous quotation.
- **Confirmed:** [HTML timer ordering](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#run-steps-after-a-timeout): “Wait until any invocations of this algorithm that had the same global and orderingIdentifier, that started before this one, and whose milliseconds is less than or equal to this one's, have completed.” This supports the equal-delay timer restriction, not universal ordering across task sources.
- **Confirmed:** [ECMA-262 HostEnqueuePromiseJob](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-hostenqueuepromisejob): “Jobs must run in the same order as the HostEnqueuePromiseJob invocations that scheduled them.” This alone does not specify timer-vs-promise order.
- **Confirmed:** [ECMA-262 PR #1250](https://github.com/tc39/ecma262/pull/1250), merged `2019-02-26T19:30:57Z`, says “there are three job queue items enqueued and dequeued before calling `f` in the `await` example” and changes this “by replacing the unconditional wrapping with a call to PromiseResolve.” The model's named spec versions are appropriate to the restricted examples.
- **Confirmed historical mechanism:** [Node PR #22842](https://github.com/nodejs/node/pull/22842): “In order to better match browser behaviour, run nextTicks (and subsequently the microtask queue) after each individual Timer and Immediate, rather than after the whole list is processed.” The cloud quote inserts “the” before “browser”; its meaning is right, but its claimed verbatim wording is slightly wrong. [Node 11 changelog](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V11.md#11.0.0): “`nextTick` queue will be run after each immediate and timer.” The PR explicitly identifies #22257 as fixed. This supports the historical timer-batching diagnosis, not the exact rerun totals.
- **Confirmed:** [V8, “Faster async functions and promises”](https://v8.dev/blog/fast-async): “there was a handy bug in Node.js 8 that caused await to skip microticks in some cases, resulting in better performance.” The page also warns: `Since then, our spec proposal was accepted, and the following "buggy" behavior is now correct.` This supports treating the Node 8 behavior differently under the two model versions.

## Review limits

This round establishes the observable finite ordering defect and abstract proof results, audits the source patch, and identifies a cancellation regression. It does not establish comprehensive HTML compliance, maintainers' intended contract, novelty, historical execution provenance, or correctness beyond the reported grammar. A useful improvement to the handoff would be a single reproduction command with tool paths and fresh-build provenance; that would separate reusable evidence from narrative run history.
