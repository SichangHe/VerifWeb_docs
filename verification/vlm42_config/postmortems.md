# Postmortems of four config-push outages

(authored by agents unless marked 🧑)

Written 2026-11-10. Nothing was posted, contacted or published.

Conventions. QUOTE = verbatim from the cited page, saved raw under /hdd1/sichangheagent/vl_meeting_work/out/vlm42_config/dl/. INFERENCE = mine. The earlier notes in vlm41_breadth/outages.md used a small-model fetch tool whose quotes were near-verbatim. Here every quote below was checked against the saved raw text (Cloudflare, Google, CrowdStrike PDF via pdftotext) or the saved page HTML (Azure). Takeaway across all four: in each case the bad data was accepted by whatever gate existed, then crashed or disabled the consumer fleet-wide within seconds to minutes.

Gaps to know. (1) The Cloudflare post shows the failing Rust code only as an image, so the exact line is not readable; only the panic message is text. (2) Google's report never mentions a validator for the policy data; the honest reading is that none is stated. (3) Azure's PIR is on a JavaScript page that returns only a header at the usual URL; the full text came from the en-gb variant of the same URL, saved as dl/azure_pir.txt. (4) Language of Service Control and the AFD data plane is not stated by the vendors.

## 1. Cloudflare, 18 Nov 2025

Source: https://blog.cloudflare.com/18-november-2025-outage/ (raw: dl/cloudflare.txt)

What the data was. A machine-learning feature list for Bot Management, regenerated by a database query and pushed to every proxy.

- "The model takes as input a “feature” configuration file. A feature, in this context, is an individual trait used by the machine learning model to make a prediction about whether the request was automated or not."
- "This feature file is refreshed every few minutes and published to our entire network"
- "the file was being generated every five minutes by a query running on a ClickHouse database cluster"
- Root change: "we made a change at 11:05 to make this access explicit, so that users can see the metadata of these tables as well." Then "there were assumptions made in the past, that the list of columns returned by a query like this would only include the “default” database: SELECT name, type FROM system.columns WHERE table = 'http_requests_features' order by name; Note how the query does not filter for the database name."
- Effect: "after the change at 11:05 the query above started returning “duplicates” of columns because those were for underlying tables stored in the r0 database." and "A change in our underlying ClickHouse query behaviour ... caused it to have a large number of duplicate “feature” rows. This changed the size of the previously fixed-size feature configuration file".

What validated it, and why it passed. The post names no validator for the file. The only check is a consumer-side limit, and the remediation list admits the file was trusted.

- "Hardening ingestion of Cloudflare-generated configuration files in the same way we would for user-generated input" (listed under "Remediation and follow-up steps"). INFERENCE: this implies the file was not ingested as untrusted input.
- Rollout was not gated: "it’s critical that it is rolled out frequently and rapidly as bad actors change their tactics quickly." and "every five minutes there was a chance of either a good or a bad set of configuration files being generated and rapidly propagated across the network."
- Tension in the post, not resolved by it: it says the limit "is set to 200, well above our current use of ~60 features", and the file "doubled in size", but also "When the bad file with more than 200 features was propagated". A doubling of ~60 is ~120, not above 200. The post does not reconcile these.

What the consumer did.

- "Each module running on our proxy service has a number of limits in place to avoid unbounded memory consumption and to preallocate memory as a performance optimization. In this specific instance, the Bot Management system has a limit on the number of machine learning features that can be used at runtime."
- "When the bad file with more than 200 features was propagated to our servers, this limit was hit — resulting in the system panicking. The FL2 Rust code that makes the check and was the source of the unhandled error is shown below:" (code is an image)
- "This resulted in the following panic which in turn resulted in a 5xx error: thread fl2_worker_thread panicked: called Result::unwrap() on an Err value"
- Old proxy: "Customers on our old proxy engine, known as FL, did not see errors, but bot scores were not generated correctly, resulting in all traffic receiving a bot score of zero."

Vendor fixes. From the same post: "Hardening ingestion of Cloudflare-generated configuration files in the same way we would for user-generated input"; "Enabling more global kill switches for features"; "Eliminating the ability for core dumps or other error reports to overwhelm system resources"; "Reviewing failure modes for error conditions across all core proxy modules". Immediate fix: "stopping the generation and propagation of the bad feature file and manually inserting a known good file into the feature file distribution queue."

## 2. Google Cloud, 12 Jun 2025

Source: https://status.cloud.google.com/incidents/ow5i3PPK96RduMcb1SsW (raw: dl/gcp.txt; the "Incident Report" entry of 13 Jun 2025 16:45 PDT)

What the data was. Quota/policy rows in a regional Spanner table, read by the Service Control binary on every API request.

- "The core binary that is part of this policy check system is known as Service Control. Service Control is a regional service that has a regional datastore that it reads quota and policy information from. This datastore metadata gets replicated almost instantly globally"
- "a policy change was inserted into the regional Spanner tables that Service Control uses for policies. Given the global nature of quota management, this metadata was replicated globally within seconds. This policy data contained unintended blank fields."

What validated it, and why it passed. The report names no validation of the policy data. It describes the code path as untested because no data had triggered it.

- "On May 29, 2025, a new feature was added to Service Control for additional quota policy checks. This code change and binary release went through our region by region rollout, but the code path that failed was never exercised during this rollout due to needing a policy change that would trigger the code."
- "The issue with this change was that it did not have appropriate error handling nor was it feature flag protected."
- "If this had been flag protected, the issue would have been caught in staging."
- The 12 Jun mini report calls the cause "an invalid automated quota update" and lists "Prevent our API management platform from failing due to invalid or corrupt data."

What the consumer did.

- "Without the appropriate error handling, the null pointer caused the binary to crash."
- "This pulled in blank fields for this respective policy change and exercised the code path that hit the null pointer causing the binaries to go into a crash loop. This occurred globally given each regional deployment."
- Recovery overload: "as Service Control tasks restarted, it created a herd effect on the underlying infrastructure it depends on (i.e. that Spanner table), overloading the infrastructure. Service Control did not have the appropriate randomized exponential backoff implemented to avoid this."

Vendor fixes (verbatim list items): "We will modularize Service Control’s architecture, so the functionality is isolated and fails open."; "We will audit all systems that consume globally replicated data. ... data replication needs to be propagated incrementally with sufficient time to validate and detect issues."; "We will enforce all changes to critical binaries to be feature flag protected and disabled by default."; "We will improve our static analysis and testing practices to correctly handle errors and if need be fail open."; "We will audit and ensure our systems employ randomized exponential backoff."; immediate: "we froze all changes to the Service Control stack and manual policy pushes".

## 3. Azure Front Door, 29 Oct 2025

Source: https://azure.status.microsoft/en-gb/status/history/?trackingId=YKYN-BWZ (same as the en-us URL; Tracking ID YKYN-BWZ; raw: dl/azure_pir_gb.html, text: dl/azure_pir.txt)

What the data was. Per-customer configuration metadata generated by the AFD control plane and consumed by the data plane at every edge site.

- "The AFD control plane generates customer configuration metadata that the data plane consumes for all customer-initiated operations including purge and Web Application Firewall (WAF) on the AFD platform."
- "A specific sequence of customer configuration changes, performed across two different control plane build versions, resulted in incompatible customer configuration metadata being generated. These customer configuration changes themselves were valid and non-malicious – however they produced metadata that, when deployed to edge site servers, exposed a latent bug in the data plane."

What validated it, and why it passed.

- "This system validates configurations at each deployment stage and advances only after receiving positive health signals from the data plane."
- "The configuration protection system waits for approximately a minute between each stage, completing on an average within 5-10 minutes globally."
- "Our configuration propagation monitoring continued to receive healthy signals – although the problematic metadata was present, it had not caused any issues. Because the data plane crash surfaced asynchronously, after approximately five minutes, the configuration passed through the protection safeguards and propagated to later stages."
- "This configuration ... completed propagation to a majority of edge sites by 15:39 UTC. Since the incompatible customer configuration metadata was deployed successfully to the majority of fleet with positive health signal, the LKG was also updated with this configuration."
- Pre-production gap: "This defect escaped detection due to a gap in our pre-production validation, since not all features are validated across different control plane build versions."

What the consumer did.

- "This incompatibility triggered a crash during asynchronous processing within the data plane service."
- "The incompatible customer configuration was processed by edge servers, causing crashes across our various edge sites. This also impacted AFD’s internal DNS service, hosted on the edge sites of Azure Front Door"
- Timing: "The data plane impact began in phases starting with our preproduction environment at 15:41 UTC, and replicated across all edge sites globally by 15:45 UTC."
- The PIR does not say which crash type (null, bounds, panic) occurred.

Vendor fixes: "We have fixed both the original control plane incompatibility, and the data plane bug described above. (Completed)"; "We are now enforcing complete synchronous processing of each customer configuration, before advancing to production stages. (Completed)"; "We have implemented additional stages in our phased configuration rollout, including extended bake time to help detect configuration related issues. (Completed)"; "We are decoupling configuration processing in data plane servers from active traffic-serving instances to isolated worker process instances, thereby removing the risk of any configuration defect impacting data plane processing. (Estimated completion: January 2026)"; "We are enhancing our testing and validation framework to ensure backwards compatibility with configurations generated across previous versions of the control plane build. (Estimated completion: February 2026)". Also: "(ii) removing asynchronous processing from the data plane, (iii) introducing an additional ‘pre-canary’ stage".

## 4. CrowdStrike, 19 Jul 2024 (Channel File 291)

Source: https://www.crowdstrike.com/wp-content/uploads/2024/08/Channel-File-291-Incident-Root-Cause-Analysis-08.06.2024.pdf, "External Technical Root Cause Analysis — Channel File 291", 2024-08-06 (raw: dl/crowdstrike.pdf, text: dl/crowdstrike.txt; read in full)

What the data was. Regex matching criteria ("Template Instances") bundled in a channel file, interpreted by the sensor's Content Interpreter.

- "Rapid Response Content is delivered through Channel Files and interpreted by the sensor’s Content Interpreter, using a regular-expression based engine."
- "Content Interpreter: Part of the sensor C++ code, which can test input strings against regexes."
- "Template Types: ... compiled into the sensor at build time." Template Instances are "Matching criteria developed by detection engineers."
- "The new IPC Template Type defined 21 input parameter fields, but the integration code that invoked the Content Interpreter with Channel File 291’s Template Instances supplied only 20 input values to match against."

What validated it, and why it passed.

- "Content Validator: Checks the validity of channel files against their definition in the Template Type Definitions file."
- "The Content Validator evaluated the new Template Instances, but based its assessment on the expectation that the IPC Template Type would be provided with 21 inputs."
- "4. The Content Validator contained a logic error ... This resulted in the problematic Template Instance being sent to the Content Interpreter."
- Why earlier tests passed: "This parameter count mismatch evaded multiple layers of build validation and testing ... In part, this was due to the use of wildcard matching criteria for the 21st input during testing and in the initial IPC Template Instances."
- "1. The number of fields in the IPC Template Type was not validated at sensor compile time"
- "the Content Validator-tested Template Instance did not observe that the mismatched number of inputs would cause a system crash when provided to the Content Interpreter by the IPC Template Type."

What the consumer did.

- "Sensors that received the new version of Channel File 291 carrying the problematic content were exposed to a latent out-of-bounds read issue in the Content Interpreter. At the next IPC notification from the operating system, the new IPC Template Instances were evaluated, specifying a comparison against the 21st input value. The Content Interpreter expected only 20 values. Therefore, the attempt to access the 21st value produced an out-of-bounds memory read beyond the end of the input data array and resulted in a system crash."
- "2. A runtime array bounds check was missing for Content Interpreter input fields on Channel File 291"
- "This is not an arbitrary memory write issue and has been independently reviewed."
- Crash dump: "performs a NULL pointer check, and then attempts a read through the invalid pointer, resulting in an out-of-bounds read and a subsequent bugcheck." It runs in a kernel driver: "csagent.sys is CrowdStrike’s file system filter driver, a type of kernel driver".

Vendor fixes: "Validate the number of input fields in the Template Type at sensor compile time" (patch "went into production on July 27, 2024"); "Bounds checking was added to the Content Interpreter function that retrieves input strings on July 25, 2024. An additional check that the size of the input array matches the number of inputs expected by the Rapid Response Content was added at the same time."; "The Content Validator is being modified to add new checks to ensure that content in Template Instances does not include matching criteria that match over more fields than are being provided as input to the Content Interpreter."; "The Content Validator was modified to only allow wildcard matching criteria in the 21st field"; "Each Template Instance should be deployed in a staged rollout."; "We have completed fuzz testing of the Channel 291 Template Type and are expanding it to additional Rapid Response Content handlers in the sensor."

## What property would have caught each (INFERENCE)

Common form: for validator V and consumer C, "V(x) accepts ⇒ C(x) does not crash" must be proved against the consumer as actually built and running, not against a spec of it. In all four, V (or the missing V) was stated against a different assumption than C used.

- Cloudflare. Property: V(file) accepts ⇒ the feature count after parsing is at most the preallocated limit (200), so the limit check in C cannot return Err. Equivalently, C must be total: no unwrap on a path reachable from file contents. The writer (SQL query) and C share no stated contract on count, and no V is described, so this property does not exist in the post to check; it would force V to exist. The "200" vs "~60 doubled" tension above means the exact trigger count is unknown to me.
- Google. Property: V(policy row) accepts ⇒ every field the quota path dereferences is non-null, or C handles null on that path. Because the failing path had never run (flag-less, no data had hit it), only a static property over all rows the table type permits (not tests on observed rows) would have found it.
- Azure. Property: V(config) accepts ⇒ C's synchronous and deferred (asynchronous) processing of the config cannot crash, including for metadata produced by any control-plane version that can co-exist. A health check that observes C for about a minute checks a weaker property (no crash within one minute); the crash came after "approximately five minutes". The needed property quantifies over C's deferred work, and over version pairs, which the PIR says were not all tested.
- CrowdStrike. Property: V(instance) accepts ⇒ every input index the instance references is below the length of the array C is actually given (20), i.e. V must use C's arity, not the Template Type Definitions file's arity (21). Equivalently, one definition of arity feeds both V and C, or C bounds-checks. This is exactly the property the vendor then added as two checks ("matching criteria that match over more fields than are being provided" in V; bounds check in C).

Not covered by this property: Google's retry herd, Cloudflare's dashboard retry backlog, and the global push speed in all four. Those need rollout and backoff properties instead.
