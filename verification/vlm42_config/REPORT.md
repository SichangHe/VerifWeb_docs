# Config pushes that crash the fleet: deeper dig

(authored by agents unless marked 🧑)

Why: the vlm41 breadth survey ranked "a validated config push crashes its consumer" as the top problem. This dig checked the postmortems, looked for the same shape in open-source Rust, and tried Verus on it. Evidence with verbatim quotes and URLs: postmortems.md, verus_notes.md, prior_work.md (same directory). Labels: FACT (sourced), INFERENCE, OPINION.

Takeaway. The bug class is real and cheap to find and prove in open-source Rust (minutes per case in Verus), but the open-source cases I found are startup bugs in operator-written config, not Cloudflare-class runtime pushes. The research contribution would be the link between validator and consumer, which no prior work I found proves. Whether that is a paper-sized contribution is a judgment call for the human.

Postmortems (FACT, postmortems.md). Cloudflare 18 Nov 2025: Rust FL2 "called Result::unwrap() on an Err value" when the bot feature file exceeded a preallocated limit of 200. Google 12 Jun 2025: Service Control crash-looped on a null pointer from blank policy fields. CrowdStrike 2024: out-of-bounds read of input 21 when 20 were supplied. Azure Oct 2025: "a crash during asynchronous processing", type not named. Correction to vlm41: only CrowdStrike had a real content validator (it wrongly assumed 21 inputs). Cloudflare and Google name no validator for the data. Azure's health checks passed because the crash came about 5 minutes later. So "validator and consumer disagree" fits one incident directly. The other three are "no check existed" or "checked too early". Open issue: Cloudflare's post says the file doubled from about 60 features, which is still under 200; I don't know how to reconcile that.

Open-source counterexamples (FACT from reading source plus Verus; nothing cloned was built or run).
Pingora (commit 3f87e92): ServerConf::validate accepts client_bind_to_ipv4: ["x"], and ConnectorOptions::from_server_conf calls .parse().unwrap() on it. The documented http_proxy_service flow reaches this unchanged, so it panics at startup. Verus file verus/pingora_conf.rs: 9 verified. It proves the counterexample, and that the consumer is panic-free exactly when every address parses. IpAddr parsing is trusted, one admit.
river (memorysafety/river, commit 0b09036f, built on Pingora): its config validation checks nothing in filter entries, and Modifiers::from_conf unwraps them. There are four accepted inputs that panic: missing kind, unknown kind, block-cidr-range without addrs, and with addrs="bad". Verus file verus/river_filters.rs: 4 verified. It proves three of the four without axioms, but the validator is modeled as "accepts everything", not copied. INFERENCE from reading: river's own --validate-configs flag panics instead of reporting the error.
No match: sozu (it re-validates at the consumer and falls back to a default) and linkerd2-proxy policy updates (they drop bad entries). Vector was only partly checked. Quickwit and rama were not checked.

Effort and blockers (FACT). About 25 min and 10 min of agent time, models of about 100 lines. Verus has no str::parse, IpAddr or serde, so the parsers become trusted predicates and the proof covers only the logic after parsing. OPINION: proving real config loaders end to end needs verified or axiomatized parsers (serde, YAML/KDL), and that is the real cost.

Prior work (prior_work.md; 7 Scholar queries, 9 papers read). The closest is ctest (OSDI'20): validators "only check configuration values" and "cannot detect ... those that cause code to fail", and it addresses this with testing, not proof. Verified parsers (EverParse, Vest, 3DGen) prove the parse is safe but stop at the parsed value. Verus and Prusti prove panic-freedom from a hand-written precondition. INFERENCE: nothing found proves the validator implies the consumer's precondition. This is an absence of evidence, and Tang SOSP'15, PCheck OSDI'16 and Ye SIGCOMM'20 were not read.

Possible research contribution (OPINION). Derive the consumer's panic-freedom precondition automatically (from Verus/Prusti obligations), and either prove the validator implies it or generate the validator from it, so the two cannot drift. A second option is degrade-not-crash: total consumers with fallbacks, the pattern sozu uses. Weaknesses: the open-source evidence is startup-time and low severity, and the big incidents are in closed code (Cloudflare FL2, Google Service Control in an unstated language, CrowdStrike in C++). Three of the four big incidents had no validator to link to. I don't know whether a hot-reload instance exists in open-source Rust. Vector's reload path is the next place to look.

Side finding (FACT): paper_collection/astrauskas2022prusti.pdf is actually the RustCompCert paper, so the file is mislabeled. It is not fixed, because that is the human's repository.
