# Independent bitset review
(authored by agents unless marked 🧑)

## Verdicts

1. **Confirmed:** the boundary bug in `out/cloud/p3_bitset_bug_independent.md`. Fresh builds of crates.io 0.137.1 with rustc 1.97.1 reproduce a caught debug panic, `attempt to shift left with overflow`, for all six built-in storage types u8/u16/u32/u64/u128/usize. Release returns respectively `255`, `65535`, `4294967295`, `18446744073709551615`, `340282366920938463463374607431768211455`, `18446744073709551615`. Exhaustively checking every other valid `(lo,hi)` and every membership bit passes for each width. Evidence: [harness](bitset/src/main.rs), [debug](bitset/debug.log), [release](bitset/release.log). Catching the panic lets every width run; our process exits successfully despite the expected panics.
2. **Confirmed:** the source diagnosis and documented valid input. Independently downloaded [pinned upstream scalar.rs](https://github.com/bytecodealliance/wasmtime/blob/9959c2c6e2d9a5c42be8b5adaea88b072089502f/cranelift/bitset/src/scalar.rs#L110-L143) is byte-identical to the newly downloaded crate source. Contract: “Panics if `lo > hi` or if `hi > Self::capacity()`.” Implementation: `let lo_rng = (one << lo) - one;`. Hence only the valid boundary `lo == hi == capacity` shifts by the width. This confirms the pinned commit, not a timeless claim about `main`.
3. **Confirmed, with scope:** job1's fixed u64 model verifies again: `verification results:: 13 verified, 0 errors`. The original fails again: `error: possible bit shift underflow/overflow`, `error: possible arithmetic underflow/overflow`, and `verification results:: 13 verified, 1 errors`. See [fixed log](bitset/fixed.log) and [original log](bitset/original.log). Both use the existing supplied Verus installation and its existing solver configuration; no shared tool was changed.
4. **Confirmed:** manual inspection of the entire proof finds no `assume`, `admit`, external-body declaration, or added axiom. `from_range_fixed` requires `lo <= hi, hi <= 64`; its postcondition covers every integer membership index. The mask implementation is checked for arithmetic safety, `lemma_range` proves the bit-vector relation, and the original with `lo < 64` is verified. `fixed_empty_at_cap` checks empty `(64,64)` and full `(0,64)`. These match the report. The source comment mentioning `(0,0)` is stale, but the report itself describes the actual check correctly.
5. **Confirmed, conditional:** `original_wrong_at_cap` proves the explicitly modeled wrapping shift, whose definition includes `lo & 63`. It does not independently establish a compiler's unchecked-shift semantics. Our release executions supply that separate evidence on this compiler/host. The report states this condition accurately.
6. **Confirmed as a model proof; otherwise overstated:** the report explicitly says, “The patch is not applied to any checkout; it is proved on a u64 model.” The generic production patch was not verified or compiled by that work. The symmetric low-mask expression is mathematically correct for the built-in primitive widths; no end-to-end production patch claim should replace the report's limitation. The early empty-range return is also a correct alternative by inspection.
7. **Confirmed:** prior upstream acknowledgment. GitHub's raw API returned cfallin's [review](https://github.com/bytecodealliance/wasmtime/pull/6020#pullrequestreview-1340339054): “LGTM. Arguably, a bitset with N bits should be legal to construct from range N..N, since N..N is empty; so if you want to put the conditional in `BitSet{,8}::from_range()` that would be fine too; but I don't mind too much either way.” The report's approximate quotation uses a comma where the original has a semicolon. [Raw review response](bitset/pr6020_reviews.json).
8. **Wrong wording:** p3 calls both search hits “unrelated DSL work,” but #6020 directly describes this predecessor defect. Its [body](https://github.com/bytecodealliance/wasmtime/pull/6020) says: “`BitSet8::from_range` will panic if the lower bound is `>= 8`, as this would cause the shift it uses to compute the lower bound value to overflow the `u8`.” The later p3 discussion correctly identifies this relationship. Describe it as a known predecessor bug with a caller workaround, not wholly novel.
9. **Confirmed only as bounded search; absence unverifiable:** fresh GitHub API searches for `from_range` and `ScalarBitSet` reproduce respectively the report's two and four result IDs. [Search outputs](bitset/search_from_range.json), [ScalarBitSet output](bitset/search_scalar.json). No exact new report appeared in these searches. This cannot prove no differently worded report exists. The [pinned file-history API](https://api.github.com/repos/bytecodealliance/wasmtime/commits?path=cranelift/bitset/src/scalar.rs&sha=9959c2c6e2d9a5c42be8b5adaea88b072089502f&per_page=100) confirms the same four commits, with oldest title “Introduce the `cranelift-bitset` crate; use it for stack maps in both Cranelift and Wasmtime (#8826)”. [Saved response](bitset/history.json). None of those commit messages names `from_range`; a broader repository-history negative was not established.
10. **Confirmed locally; global impact remains inference:** independently fetched [instructions.rs](https://github.com/bytecodealliance/wasmtime/blob/9959c2c6e2d9a5c42be8b5adaea88b072089502f/cranelift/codegen/src/ir/instructions.rs#L1018-L1028) contains `if lower_bound < BitSet8::capacity() {` and “this would already describe the empty set so instead we leave `ints` in its default empty state.” Its calls avoid the failing lower bound. The report's call-site line list is incomplete: there are further constant calls after line 1288, also safe. The [upstream test](https://github.com/bytecodealliance/wasmtime/blob/9959c2c6e2d9a5c42be8b5adaea88b072089502f/cranelift/bitset/tests/bitset.rs#L57-L77) omits `(N,N)`. A repository-wide absence of internal exposure was not established here; retain the report's “Belief” qualification. Low severity and suitability as a verification example remain opinions, consistent with the demonstrated arithmetic/API error rather than proven application impact.
