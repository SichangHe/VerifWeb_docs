## 1. cssparser identifier classification

- **Confirmed:** “Against the real crate 0.38.0, `-\LF` gives Ident("-").” Rebuilt the Cargo reproduction against `cssparser="=0.38.0"`; output: `"-\\\n": Ident("-")`, then `Delim('\\')`, then `WhiteSpace("\n")`. CR and form-feed produce the same classification. `@-\\\n` produces `AtKeyword("-")`.
- **Confirmed:** “@csstools/css-tokenizer 4.0.2 and the spec give Delim('-').” Reran the reference: `"-\\\n" => delim-token:"-" delim-token:"\\" whitespace-token:"\n" EOF-token:""`. CSS Syntax §4.3.8 says, “Otherwise, if the second code point is a newline, return false.” Its §4.3.9 says, “or the second and third code points are a valid escape, return true.” Thus backslash/newline after the hyphen is not a valid escape. Source: https://drafts.csswg.org/css-syntax-3/#starts-with-a-valid-escape and https://drafts.csswg.org/css-syntax-3/#would-start-an-identifier (downloaded text retained in `servo_checks/css_spec.txt`; quoted whitespace normalized).
- **Confirmed by source inspection; fix not compiled:** “The fix is `has_newline_at(2)` at tokenizer.rs:931.” The hyphen branch already reads the backslash at offset one, then incorrectly tests `b'\\' => !tokenizer.has_newline_at(1),`. Offset two is the following newline. Source: https://github.com/servo/rust-cssparser/blob/v0.38.0/src/tokenizer.rs#L926-L935.
- **Confirmed:** “It is already reported as servo/rust-cssparser#440 (open).” GitHub API returned title “is_ident_start reads the wrong byte for a hyphen before a backslash” and `"state":"open"`: https://github.com/servo/rust-cssparser/issues/440.
- **Overstated severity conclusion:** “Impact is low, because a stray `\` Delim follows in either case.” The trailing delimiter is confirmed; it does not establish overall severity or equivalent behavior in every grammar. Token and serialization differences are demonstrated; browser-level effects were not tested. Keep “low” as an assessment, not a verified fact.

- **Confirmed source defect:** “current_line_number u32 overflow.” Real crate source declares `current_line_number: u32` and increments it with `self.current_line_number += 1;`. Source: https://github.com/servo/rust-cssparser/blob/v0.38.0/src/tokenizer.rs#L476.
- **Confirmed release reproduction:** “In release it reports the wrong line number only.” Rebuilt with `overflow-checks=false`; output: `token=Ok(Ident("a")) true_line0=4294967306 reported_line0=10 col=2`. This confirms correct token and wrong line for this input. “Only” is not a proof about downstream consumers or every input.
- **Confirmed debug reproduction:** “A real repro with 2^32+10 newlines panics in debug.” Fresh full-input run exited 101 with `cssparser-0.38.0/src/tokenizer.rs:476:9` and `attempt to add with overflow`. Logs: `servo_checks/lineno_debug.log` and `servo_checks/lineno_release.log`.
- **Confirmed only as a limited search result:** “No upstream report was found.” My fresh `gh search issues current_line_number --repo servo/rust-cssparser --json title,url` returned `[]`. This cannot prove no report exists under other wording.
- **Unverifiable practical claim:** “Not realistically reachable from the web (belief, untested)” and “practically irrelevant.” The reproducer allocates over 4 GiB. Neither browser limits nor real web reachability were measured; preserving the explicit belief/untested qualification is necessary.

## 3. Servo MP4 matcher

- **Confirmed:** “The real unmodified mime_classifier.rs panics at line 496.” The harness includes the pinned real source and stubs only `LoadContext`. Rebuilt tests reproduce `range start index 16 out of range for slice of length 12` for box sizes 0, 8, and 12; the `mp42` brand control passes. The classifier test fails with that panic, as expected for the defect. Source: https://github.com/servo/servo/blob/d275164b2bf624ee5844b22522d10c81b8f606ab/components/shared/net/mime_classifier.rs#L463-L502. The offending expression is `data[16..box_size]`; guards admit an undersized box.
- **Confirmed:** “It is already reported as servo/servo#47603 (open). Fix PR #47607 was closed unmerged.” API issue title: “mime_classifier.rs: Indexing error in `Mp4Matcher::matches` for box_size < 16”, state `open`; PR title: “net: Fix mime sniff mp4 bug”, state `closed`, merged `false`. Sources: https://github.com/servo/servo/issues/47603 and https://github.com/servo/servo/pull/47607.
- **Confirmed as a source-level inference, not browser execution:** “Reachability through ServoParser::load_document is inferred from reading code, not run.” The caller passes `LoadContext::Browsing`, `NoSniffFlag::Off`, content type, and `resource_header` to `MimeClassifier::default().classify`. Source: https://github.com/servo/servo/blob/d275164b2bf624ee5844b22522d10c81b8f606ab/components/script/dom/servoparser/mod.rs#L1131. Exact process/pipeline consequences remain untested.
- **Unverifiable provenance:** “The spec quote was written from memory.” I cannot independently establish how the earlier author wrote it. Its conclusion is correct: the freshly fetched standard says “Let bytes-read be 16” and “While bytes-read is less than box-size, continuously loop through these steps”, followed by “Return false.” A box below 16 skips the loop. Use the actual standard instead of the earlier reconstructed quotation: https://mimesniff.spec.whatwg.org/#matches-the-signature-for-mp4. Download retained in `servo_checks/mime_spec.txt`.

## 4. Servo Blob.slice

- **Confirmed by source and copied-code execution:** “mozjs 0.26.14 clamps 1e19 to 2^53-1, so `b.slice(1).slice(1e19)` does not overflow.” mozjs specifies `impl_num!(i64, 0, -(1 << 53) + 1, (1 << 53) - 1);`; its Clamp conversion calls `clamp_to`. Source: https://docs.rs/crate/mozjs/0.26.14/source/src/conversions.rs (local lines 130, 239, 343). Blob IDL uses `[Clamp] long long`: https://github.com/servo/servo/blob/d275164b2bf624ee5844b22522d10c81b8f606ab/components/script_bindings/webidls/Blob.webidl. Rebuilt copied-code output: `clamp(1e19)=9007199254740991`, then `start: 9007199254740992`, `abs=10..10`. The original single-step overflow claim is wrong.
- **Confirmed arithmetic defect; browser consequence inferred:** “About 1024 chained `slice(1e19)` calls do overflow: debug builds panic, and release returns the whole blob instead of an empty one.” Fresh debug run panics with `attempt to add with overflow`; release wraps at zero-based `i=1024` to `-9214364837600035840`, eventually prints `abs=0..10`. Precisely, this is the 1025th large addition after the initial `slice(1)`, not the 1024th addition as the detailed report says. The summary's “about” is fair.
- Source confirms why the copied arithmetic applies: `start: parent_range.start + start.unwrap_or_default(),` and `end: end.map(|end| end + parent_range.start).or(parent_range.end),` in https://github.com/servo/servo/blob/d275164b2bf624ee5844b22522d10c81b8f606ab/components/script/dom/file/blob.rs#L324-L329. `BlobImpl::new_sliced` directly stores `BlobData::Sliced(parent, range)`, without normalizing it: https://github.com/servo/servo/blob/d275164b2bf624ee5844b22522d10c81b8f606ab/components/shared/constellation/structured_data/serializable.rs#L330. Thus intermediate offsets accumulate. Full JavaScript/Servo execution remains unverified; label the reproduction an arithmetic model.
- **Confirmed scope qualification:** “The repro uses copied code; Servo was not built.” This is demonstrably a standalone Rust arithmetic reproduction, and this review also did not build Servo. It cannot independently establish every action of the prior reviewer.
- **Confirmed only as a limited search:** “No upstream report was found.” Fresh `gh search issues 'Blob slice overflow' --repo servo/servo --json title,url` returned `[]`; existence of differently titled reports remains unknown.
- **Confirmed source-level side finding:** “a negative start on a sliced blob may use the wrong base.” For a ten-byte blob, `slice(2,8).slice(-1)` stores start `2 + (-1) = 1`, end `8`, yielding range `1..8`; expected `7..8`. The standard says “If start is negative, let relativeStart be max((originalSize + start), 0). Otherwise, let relativeStart be min(start, originalSize).” Here originalSize must be the six-byte intermediate slice. Source: https://w3c.github.io/FileAPI/#slice-method-algo (download retained in `servo_checks/file_spec.txt`; quoted whitespace normalized). This follows directly from the inspected branch and range conversion; browser execution was not performed.
