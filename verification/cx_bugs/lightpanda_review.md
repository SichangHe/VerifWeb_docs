## Claim-by-claim verdicts

1. **Confirmed by execution:** E0/E1's HTTP-versus-WebSocket split. Baseline direct fetch/XHR and their 301/302/307/308 redirects return data; a scheme-independent URL pattern blocks all those HTTP cases while WebSocket receives the server's message. `baseline.log`, `url.log`, and `server-18003.log` contain the results. The server records `GET /ws upgrade=True origin=http://127.0.0.1:18001` and `ws handshake completed (101 sent)`. Original timestamps and exact original request counts remain historical claims, not independently authenticated logs.

2. **Confirmed by execution:** E3's WS-specific pattern still allows WebSocket, while HTTP succeeds (`ws_pattern.log`). **Confirmed by source, not separately rerun:** E2's HTTP-specific pattern, the `http://` constructor variant, and upper-case-path variant. The connection path contains no URL-blocklist check, and WebSocket initialization explicitly accepts `http:` and `https:` and maps them to WS schemes. The report correctly describes an upper-case path; its result key `ws_upper_case_host` is misleading because the numeric host has no letters.

3. **Confirmed by execution, with scope correction:** E4 direct document, 302 document redirect, meta refresh, synchronous `location.href`, direct/302 scripts and enabled iframes are blocked. Logs are `document.log`, `document_redirect.log`, `meta.log`, `location.log`, and `subresources.log`. Example: `$msg="blocked url" $page=2 url=http://127.0.0.2:18003/meta`. **Overstated as experimental coverage:** the opening says “Covers 301/302/307/308 used by fetch, XHR, the top-level document, iframes and `<script>`”; E4 documents only 302 for document navigation, and does not enumerate all four statuses for scripts/iframes. My rerun covers all four only for fetch/XHR, and 302 for other resource kinds. The broader behavior is supported by the shared redirect path, not by an independently demonstrated full matrix.

4. **Unverifiable as historical observations:** the original empty E4 server logs, exact `page_status.skipped.image`, original disabled-iframe log, and timer-navigation early exit were not supplied as original runnable pages/logs. The report appropriately marks image skipping and timer navigation as non-evidence. No blocking conclusion should be inferred from a resource not being requested.

5. **Confirmed by execution:** E5's CDP `Network.setBlockedURLs` bypass (`cdp.log`). URL patterns block HTTP while WebSocket receives data. Failures really use `"type":"Ping"`. **Confirmed by source, not separately rerun:** CLI blocking in serve mode and rejection of legacy `urls` parameters; `urlPatterns` is a required field. The exact legacy error code `-31998` remains unverified. Whether `Ping` is the correct protocol label was not checked against Chromium/CDP semantics; the report labels that concern as belief appropriately.

6. **Confirmed by execution:** E6 adblock bypass. A plain filter containing `127.0.0.2:18003` blocks the HTTP controls while WebSocket receives `hello-from-18003` (`adblock.log`). This validates the mechanism with a broader filter than the report's two pathname filters.

7. **Confirmed by execution:** E7 CIDR mitigation for this direct connection. `--block-cidrs 127.0.0.2/32` produces blocked HTTP and `"ws":"error"` (`cidr.log`). **Overstated as tested fact:** “Mitigation that works today (fact, E7): `--block-cidrs` / `--block-private-networks`.” E7 tests only CIDRs. Private-network blocking shares the same callback and is strongly source-supported, but was not executed in the original reported experiment or this review. These are IP filters, not hostname filters; they cannot distinguish two names using the same target address. No universal protection claim across proxies or other untested network configurations is established.

8. **Confirmed by source:** S1–S4's ordinary HTTP pipeline versus direct WebSocket connection explanation; S5's IP callback installation; S6's shared CDP list and required `urlPatterns`; S7's full-URL, ASCII-case-insensitive wildcard matching. Relevant exact source excerpts and links follow. The search claim is also confirmed: outside `HttpClient.zig` and `UrlBlocklist.zig`, the three identifiers occur only in `src/browser/tools/search.zig`. **Overstated if read literally:** “the only place the URL blocklist ... [is] checked” excludes `blocksUrl` checks in search; the report itself acknowledges those. The precise claim is that the shared HTTP transfer check is absent from WebSocket's connection path.

9. **Confirmed as a limited inference:** a matching URL deny rule is bypassable by a page opening WS; outbound upgrade and inbound payload were observed. **Overstated as payload-send evidence:** “E1–E3 show both directions” establishes a handshake request and received application data, not a call to `WebSocket.send` carrying an application payload. Exfiltration in a URL is possible from the shown path, but bidirectional application messaging was not directly tested. “Any page script” must retain normal constructor/port/origin/network constraints. TLS `wss://`, Workers, and 3xx upgrades remain **unverifiable by execution** here; source supports shared-path concerns, not the full outcomes. In particular, receiving a 3xx does not itself demonstrate following it.

10. **Unverifiable intent/opinion:** whether the gap is an omission rather than design, and whether it is a good formal-verification target. Both are correctly marked belief/opinion in the report. The proposed spec “Every outbound connection is preceded by `isUrlBlocked(url) == false`” is **overstated as a ready specification**: the actual function accepts a `Transfer`, explicitly exempts internal requests, and reasons about adblock resource context. A useful specification must define those exceptions and contexts; the missing WS guard itself is confirmed.

11. **Confirmed from inspected harness:** it emits a valid SHA-1/GUID accept response, sends a text frame, sleeps one second, and closes TCP without a close frame. The original `1006` events are consistent with that closure; exact original event strings and the claim that no upstream report was filed remain **unverifiable historical claims**. The report's stated limitations—one nightly/Linux, loopback and plain HTTP/WS, no TLS—accurately bound the evidence and also apply to my rerun.
